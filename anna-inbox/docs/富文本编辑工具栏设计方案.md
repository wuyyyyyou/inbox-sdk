# 富文本编辑工具栏设计方案

## 1. 目的与范围

在邮件详情抽屉的撰写区增加富文本编辑工具栏，替代当前回复和转发正文使用的纯文本 `textarea`。首期仅覆盖邮件回复与转发的可编辑正文，不扩展到 AI 对话、搜索框、收件人、主题或其他文本输入区。

已确认的首期能力如下：

- 加粗、斜体、下划线。
- 预设字号。
- 文字颜色。
- 有序列表、无序列表。
- 插入、修改和移除超链接。
- 撤销、重做。
- 常用快捷键：`Ctrl/Cmd+B`、`Ctrl/Cmd+I`、`Ctrl/Cmd+U`、`Ctrl/Cmd+Z`、`Ctrl/Cmd+Shift+Z`。
- 桌面端完整展示工具栏；移动端工具栏横向滚动，不隐藏任何首期功能。

删除线、引用块、清除格式、标题层级、字体家族、图片和表格不属于本期范围。

## 2. 当前状态与问题

`MailDetailDrawer.tsx` 中的回复和转发正文均为受控 `textarea`，草稿、计划发送和发送回复目前以纯文本 `body` 传递。转发发信已支持额外的 `body_html`，回复链路尚未建立 HTML 数据契约。

只在前端叠加工具栏无法满足格式保留要求：草稿再次打开、计划发送和最终邮件发送都会退化为纯文本。因此本功能需要同时升级前端草稿模型、前端调用边界和 Executa 的草稿/发信数据边界，使 HTML 成为可持久化格式，而纯文本继续作为兼容展示和 MIME 文本备选。

## 3. 交互设计

### 3.1 工具栏布局

工具栏位于撰写区正文上方、收件人和主题等邮件头字段下方。按钮使用现有的图标按钮视觉规范，并提供 `aria-label` 与悬浮提示。

从左到右排列：

1. 撤销、重做。
2. 加粗、斜体、下划线。
3. 字号下拉菜单。
4. 文字颜色选择器。
5. 无序列表、有序列表。
6. 超链接。

工具栏按功能组以细分隔线区分。当前选区或光标所在格式应显示激活状态；无可撤销或重做的历史记录时，对应按钮禁用。

### 3.2 文本格式行为

- 未选中文本时，行内格式命令影响后续输入；选中文本时，仅变更选区。
- 字号使用固定预设 `12`、`14`、`16`、`18`、`20`、`24` px，默认字号为 `14` px。
- 颜色选择器提供一组与现有邮件界面协调、具备可读性的固定色板，并显示当前颜色。首期不提供自定义色值输入。
- 列表命令作用于当前段落或所选多个段落；再次点击同类列表可取消列表。
- 仅保存语义化、内联样式受控的 HTML：段落、换行、强调、列表、链接、字号和颜色。不得保存脚本、事件属性、嵌入对象或任意外部样式。

### 3.3 超链接行为

- 选中文本后点击链接按钮，弹出锚定在工具栏或选区附近的小浮层，显示 URL 输入框以及确认、移除操作。
- 未选中文本时，浮层同时显示链接文字和 URL 输入框；确认后插入链接文字。
- URL 仅接受 `https:`、`http:` 和 `mailto:` 协议。空值、无效协议或不合法 URL 显示字段内错误，不修改正文。
- 光标位于已有链接内时，浮层预填链接地址；确认用于修改地址，移除只移除链接而保留文字。
- 打开浮层前必须保存 Selection/Range，确认或取消后恢复编辑区焦点和选区，确保格式命令不会错误作用于其他位置。

### 3.4 键盘与焦点

- 快捷键仅在富文本正文获得焦点时接管；浏览器或系统保留快捷键不受影响。
- 按钮操作不可导致正文丢失焦点或选区。鼠标按下阶段阻止默认焦点转移，再在命令完成后恢复选区。
- `Tab` 按既有表单顺序访问工具栏、编辑区和发送按钮；每个无文字图标按钮必须通过辅助技术获得名称。

## 4. 数据与安全设计

### 4.1 编辑器内部模型

编辑区改为受控 `contenteditable`。组件维护以下两个值：

- `body_html`：经过白名单净化的 HTML，是格式的权威值。
- `body`：从 `body_html` 提取的纯文本，用于纯文本 MIME 部分、空内容判断和不支持 HTML 的兼容场景。

纯文本草稿加载时转换为安全 HTML 后显示：按换行拆分为段落或换行，不将原始文本作为 HTML 解析。旧草稿因此保持原内容，不会因升级产生标签注入。

### 4.2 持久化与发送契约

回复与转发草稿均新增可选 `body_html` 字段，并与 `body` 一起保存。现有仅有 `body` 的存量草稿继续可读。

- 自动保存和手动恢复必须保存、读取并恢复 `body_html`。
- AI 生成的纯文本草稿在进入编辑器时按纯文本转换，不把 AI 输出作为 HTML 直接渲染。
- 计划回复、计划转发、立即回复和立即转发均传递 `body` 与 `body_html`。
- Executa 在生成 Gmail MIME 时，使用 `body_html` 生成 `text/html` 部分，使用 `body` 生成 `text/plain` 部分；缺少 `body_html` 时保持现有纯文本行为。
- 发送前在前端和后端均执行 HTML 净化。后端为最终信任边界，不能依赖前端净化结果。

HTML 白名单只允许本功能所需的元素与属性：`p`、`br`、`strong`、`em`、`u`、`span`、`ul`、`ol`、`li`、`a`；链接仅允许上述三种协议，`span` 仅允许字号和文字颜色对应的受控样式。其他标签和属性一律删除。

### 4.3 撤销与重做

本期使用编辑器会话内历史记录。每一次用户输入或格式操作生成历史快照；连续输入按短时间窗口合并，避免逐字符撤销。历史不写入草稿存储，重新打开草稿后从空历史开始。

AI 替换、切换回复/转发模式、加载另一封邮件、丢弃草稿和成功发送均清空当前编辑器历史。保存草稿不会清空历史。

## 5. 技术实现边界

前端不引入新的富文本 UI 依赖。实现为一个局部、可复用的编辑器组件，负责编辑 DOM、选区、格式命令、HTML 净化、纯文本派生和历史；`MailDetailDrawer` 继续负责草稿状态、自动保存和发送调度。

格式命令基于浏览器 Selection/Range API 实现，不能依赖未受控 DOM 作为数据源。每次 `input`、粘贴、格式命令和历史恢复后，先净化 HTML，再同步受控状态。粘贴内容只保留受白名单支持的格式；不支持的格式转换为纯文本或允许的基础结构。

为避免正文渲染与编辑隔离失效，编辑器显示的 HTML 必须使用与邮件展示相同或更严格的净化策略。不得使用 `dangerouslySetInnerHTML` 绕过净化。

## 6. 影响文件与预期改动

实施阶段预计只修改与此功能直接相关的以下区域：

- `anna-inbox/src/features/mail-detail/`：新增富文本编辑器组件，替换撰写区正文输入，并调整草稿和发送参数。
- `anna-inbox/src/types/mail.ts`、前端 API facade 与关联状态：为草稿/计划发信数据增加 `body_html`。
- `inbox-tool/src/anna_inbox_executa/` 与邮件发送、草稿存储边界：接收、存储、净化并发送 `body_html`。
- 对应的前后端测试：格式往返、净化、纯文本回退、超链接协议、历史操作以及发信 MIME。

不修改 AI 工具调用入口、账户连接、附件上传机制、已读邮件正文渲染策略或无关页面样式。

## 7. 验收标准

1. 回复和转发编辑区均能使用全部首期工具，且工具栏在桌面与移动端可访问。
2. 格式化后的内容在继续输入、切换选区、撤销/重做后符合预期，不丢失正文。
3. 超链接可创建、修改、移除；非法协议不能写入正文。
4. 草稿自动保存后重新打开，字号、颜色、列表、强调和链接均保留。
5. AI 生成的纯文本草稿可继续编辑，且不会被当作 HTML 执行或渲染。
6. 计划发送和立即发送的邮件同时包含正确的 `text/plain` 和 `text/html` 内容；不支持 HTML 的收件方仍能读取纯文本。
7. 包含脚本、事件属性、危险 URL 或不允许标签的输入，在前后端均不会被保存或发送。
8. 现有纯文本草稿、转发引用内容、附件和发送 guardrail 保持现有行为。

## 8. 审批项

请审批以下设计决策后再进入编码：

1. 首期范围限定为邮件回复与转发正文。
2. 字号预设为 `12/14/16/18/20/24` px，颜色使用固定色板。
3. 编辑器采用受控 `contenteditable`，不新增前端依赖。
4. 富文本以经过白名单净化的 `body_html` 持久化和发送，同时保留派生的纯文本 `body`。
5. 撤销/重做仅在当前编辑会话有效，不跨草稿重新打开持久化。
