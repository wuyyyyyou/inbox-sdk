# Brief / Handle 页面布局优化方案

> 状态：推荐布局已完成，持续打磨中。
> 适用范围：Anna Inbox 前端当前 React 结构，重点是 `src/features/handle/HandleView.tsx` 打开的 Brief 卡片详情页。
> 背景：用户反馈 Brief 详情页布局混乱、视觉不好看、操作区不够稳定。本文记录从截图出发的 UI/UX 优化方向，后续按小步验收逐项落地。

## 0. 当前进展

截至本轮，本文档中的“推荐布局”已经完成第一阶段落地，保持了前后端契约不变：

- Handle 详情页已切换为桌面两栏工作台：左侧邮件上下文，右侧处理与草稿。
- 详情页模式下外层 `.app-content` 不再作为主滚动容器，左右两列改为独立滚动，并保留稳定滚动槽。
- 修复了部分 Handle 页面整体下沉、顶部留白异常的问题。
- 原文入口已改为更轻量的 disclosure row，展开后留在左侧列，不再影响右侧处理区。
- `Thread context` 维持折叠入口，展开后只影响左侧列滚动。
- 右侧 Draft reply 区已稳定为独立处理列，`Reply now`、`No action needed`、`Handled manually`、`Next card` 保持可见。
- 草稿编辑区已支持按内容自动撑高，并提高了默认高度，避免首次生成草稿后用户还要先手动拖拽才能编辑。
- `Next card` 已固定在右侧操作区最右侧。

当前仍保留为后续打磨项的内容：

- 评估是否合并 `Email summary` 和 `Anna noticed` 为统一 `Insight` 区域。
- 继续微调视觉层级、块间距和桌面/移动端细节。

## 一、问题判断

截图对应的主要不是 Brief 卡片列表页，而是打开单张 Brief 卡片后的 Handle 详情页。

当前详情页的问题不是单个按钮样式，而是信息架构和视觉层级不清：

- `Original email body hidden`、`Email summary`、`Thread context`、`Anna noticed`、`Draft reply` 都被做成相近重量的块，用户很难判断先看哪里。
- 页面整体是一列模块堆叠，核心任务“理解邮件并处理/回复”被辅助信息挤压。
- `Draft reply` 是主要操作区，但在第一屏中不够突出，生成草稿后编辑区域也容易受其他控件挤压。
- 浅色、浅紫、浅蓝边框和半透明背景重复较多，页面有“多层卡片叠在一起”的感觉。
- 原文和线程上下文属于辅助信息，但占据了接近摘要和草稿区的视觉重量。
- 展开线程或出现滚动条时，页面布局容易发生跳动，影响稳定感。

## 二、优化目标

本轮优化以行为等价为前提，不改 Executa 工具契约、不改 Python 后端、不改卡片字段语义。

目标是让 Handle 详情页变成更像一个邮件处理工作台：

- 用户第一眼能看清楚“这是什么邮件、Anna 判断了什么、我现在能怎么处理”。
- 邮件上下文和处理操作分区明确。
- 详情页滚动边界稳定，不因为某个区域展开导致整个页面跳动。
- 草稿生成前和生成后都保持可用，尤其是草稿编辑区要足够大。
- 移动端仍保持单列，不能出现左右栏挤压或按钮被裁切。

## 三、推荐布局

### 3.1 桌面布局

桌面或宽屏下采用两栏工作台：

```text
┌──────────────────────────────────────────────────────────────┐
│ Back to brief                                                 │
├──────────────────────────────────────────────────────────────┤
│ 邮件标题                                  状态 badge          │
│ 发件人 / 主题 / 时间 / mailbox                                │
├───────────────────────────────┬──────────────────────────────┤
│ 左侧：邮件上下文              │ 右侧：处理与草稿              │
│ - 原文轻量 disclosure         │ - Draft reply                 │
│ - Email summary               │ - reply mode / preferences    │
│ - Thread context accordion    │ - decision / revise controls  │
│ - Anna noticed / summary      │ - draft textarea              │
│ - 展开原文或线程内容          │ - Reply / No action / Next    │
└───────────────────────────────┴──────────────────────────────┘
```

左侧是邮件上下文，右侧是处理区。两侧都可以作为独立滚动容器，避免整个详情页一起滚动。

### 3.2 移动布局

移动端回到单列：

```text
标题
摘要 / Anna noticed
Draft reply
线程上下文
原文 disclosure / 原文内容
底部处理按钮
```

移动端不强制两栏，也不使用固定高度侧栏，避免小屏裁切操作区。

## 四、模块级优化方案

### 4.1 Header

当前标题区信息密度不够清晰。

建议：

- Header 横跨两栏。
- 标题保持为最大文本层级。
- 第二行显示发件人、邮件主题、时间、message count、mailbox。
- 状态 badge 固定在右上角，例如 `Needs reply`、`Needs review`、`Reply ready`。

验收标准：

- 标题和状态一眼可见。
- 发件人和主题不和正文模块混在一起。
- 长标题不会挤压 badge 或溢出。

### 4.2 原文入口

原文默认隐藏是正确的，但当前提示块视觉重量过高。

建议：

- 未展开时改成轻量 disclosure row。
- `Show full email` 放在同一行右侧。
- 有附件时保留提示，但不单独占大块。
- 展开后原文进入左侧滚动列，不影响右侧草稿区。

验收标准：

- 未展开原文时页面不再被一个大卡片占据。
- 展开原文后可以阅读长邮件，右侧操作区保持可用。

### 4.3 Email summary / Anna noticed

当前 `Email summary` 和 `Anna noticed` 语义接近，容易重复。

建议：

- 第一阶段先保留两个模块，只调整层级。
- 后续可合并为一个 `Insight` 区域：
  - 上半部分展示邮件事实摘要。
  - 下半部分展示 Anna 的判断和 reply focus。
- Bullet 样式收敛，减少重复的 AI avatar 或装饰。

验收标准：

- 用户能快速读到“发生了什么”和“我该做什么”。
- 不出现两个看起来同等重要、内容又重复的摘要块。

### 4.4 Thread context

线程上下文应是可展开辅助信息，不应默认抢占主操作区。

建议：

- 默认折叠为一行：`Thread context · sender · time · N messages`。
- 展开后左侧内部滚动，不推动整个详情页。
- 多消息时保留现有 hidden messages loader。
- metadata grid 用紧凑行距，减少“表格式大卡片”的占位。

验收标准：

- 折叠态轻，不干扰摘要和草稿。
- 展开态稳定，不导致右侧跳动或页面整体跳动。

### 4.5 Draft reply

草稿区是详情页的主操作区，应比辅助信息更稳定。

建议：

- 右侧作为独立处理列。
- 初始态展示 reply decision、reply mode、draft preferences 和生成按钮。
- 生成草稿后 textarea 至少保持可编辑的实用高度。
- 操作按钮区域始终可见或可通过右侧滚动自然访问。
- `Next card` 不能因为生成草稿后消失。

验收标准：

- 未生成草稿时，用户能清楚看到需要做的决策。
- 生成草稿后，textarea 不应过小。
- `Reply now`、`No action needed`、`Handled manually`、`Next card` 在右侧操作流中保持可发现。

## 五、滚动策略

推荐滚动策略：

- 外层 `.app-content` 在详情页模式下不作为主要滚动容器。
- 左侧上下文列独立滚动。
- 右侧操作列也独立滚动。
- 两列使用常驻滚动槽，避免滚动条出现/消失导致布局跳动。
- 窄屏单列时恢复页面整体滚动。

验收标准：

- 展开线程前后，左右栏宽度和位置不跳。
- 长邮件原文只影响左侧滚动。
- 长草稿或较多控件只影响右侧滚动。
- 移动端仍能从上到下自然浏览完整内容。

## 六、视觉风格调整

建议整体向“轻量工作台”收敛：

- 减少大圆角卡片嵌套，详情页内部块圆角控制在 10-12px 左右。
- 减少半透明大块的数量，辅助信息使用更轻的边框或 dashed disclosure。
- 摘要和草稿区可以保留更实的背景，作为主要视觉锚点。
- 保持现有 Anna Inbox 的柔和色调，但避免所有模块都使用近似浅紫高亮。
- 按钮宽度和排列要稳定，避免生成草稿前后位置大幅变化。

## 七、建议实施顺序

按小步验收推进：

1. 重排详情页骨架。
   - Header 横跨顶部。
   - 内容区分为左侧上下文列和右侧处理列。
   - 不改工具调用和业务逻辑。
   - 当前状态：已完成。

2. 调整滚动边界。
   - 详情页模式关闭外层整体滚动。
   - 左右两列独立滚动。
   - 常驻滚动槽，避免布局跳动。
   - 当前状态：已完成。

3. 优化右侧处理区。
   - 保证草稿生成前后按钮和 `Next card` 不丢失。
   - 提高 textarea 可编辑空间。
   - 保持右侧内部滚动可用。
   - 当前状态：已完成。

4. 合并或降噪摘要模块。
   - 评估是否把 `Email summary` 和 `Anna noticed` 合并为 `Insight`。
   - 减少重复文案和重复装饰。
   - 当前状态：暂未开始。

5. 打磨视觉细节。
   - 调整边框、圆角、间距、按钮尺寸。
   - 检查桌面和移动端。
   - 当前状态：进行中。

## 九、验证清单

每一步改完后至少验证：

- `npm run build`
- 首次进入 Handle 详情页。
- 点击 `Show full email` 后长原文展示。
- 展开 / 折叠 `Thread context`。
- 生成草稿前的决策输入状态。
- 生成草稿后的 textarea 编辑状态。
- `Reply now`、`No action needed`、`Handled manually`、`Next card` 可见且可点击。
- 窄屏下无内容重叠、无按钮被裁切。
