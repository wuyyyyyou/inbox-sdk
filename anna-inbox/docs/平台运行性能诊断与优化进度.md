# 平台运行性能诊断与优化进度

状态：App `2.1.1` / Tool `2.2.1` 已完成首期优化和调用链安全诊断；AI Ask 已限定当前活动邮箱，等待正式环境回归与耗时采样。

## 范围与优先级

本专项先处理「本地快、正式平台慢」的公共链路，优先级如下：

1. Executa 连接稳定性与首次加载。
2. 首页邮件刷新、账户切换和正文加载性能。
3. Gmail 外部变更回流。
4. 邮件正文排版与交互体验。

不在本阶段直接改变 Gmail 的删除、发送或标签安全约束。

## 已确认的差异

本地开发环境从本地 token 文件和本地 JSON 缓存读取数据；正式平台需要通过 Host Reverse RPC 获取 Google Connected Account 的短期 token，并通过 APS 读写缓存。相同的业务循环在平台上会叠加跨进程和网络往返。

首页 All-mail 快照最多预热 400 封邮件。优化前，`search_gmail` 和每封 `fetch_message_summary` 都会调用 `get_access_token`；在正式平台中，这意味着一次刷新可能发起约 400 次 `credentials/getToken` Reverse RPC。本地 token 读取不具备这项成本，因此会出现显著体感差异。

APS 分页缓存此前每次 `list_cached_emails` 都会额外读取第一页，用于检测历史缓存字段。这会增加一次 Host Storage Reverse RPC；首屏及后续流式分页会累积该延迟。

## 已完成优化

### 1. Gmail 摘要批次复用短期 token

- `live_search_metadata_and_cache` 在单次调用内通过 `ContextVar` 保存第一个 Gmail 请求取得的短期 token。
- 并发摘要 worker 使用 `copy_context()` 继承同一个调用上下文，不再各自请求 token。
- `list_gmail_emails_page` 也把首个 Gmail 列表请求的上下文传递给本页摘要 worker。
- token 不进入前端、APS、local storage 或日志；作用域结束后恢复原上下文。

效果预期：

| 场景 | 优化前 | 优化后 |
| --- | --- | --- |
| 首页首次刷新 400 封邮件 | 身份校验 1 次 + 最多约 400 次 token Reverse RPC | 身份校验 1 次 + 摘要批次 1 次 token Reverse RPC |
| Gmail 加载更多 100 封邮件 | 列表请求 1 次 + 最多约 100 次 token Reverse RPC | 列表请求取得 1 次 token，供本页摘要复用 |

### 2. APS 分页缓存版本化

- All-mail 分页元数据新增 `schema_version: 2`。
- 已升级缓存直接使用元数据，不再额外读取第一页做历史字段探测。
- 旧缓存仅在首次读取时从索引重建为新版本；这是一次性迁移成本。

## 后续方案

### 正式环境采样

为以下阶段记录时间、结果和错误分类，且不得记录 token、authorization header 或邮件正文：

1. Runtime connect、`initialize`、Connected Account discovery；当前已覆盖 `credentials.list_accounts`。
2. `credentials/getToken`、Gmail 列表、Gmail metadata、APS 缓存读写；当前已覆盖 `credentials.get_token`、`gmail.http`，APS 仍待覆盖。
3. 缓存命中首页、缓存未命中首页、账户切换、邮件详情加载。
4. Executa 重启、Host RPC 超时和前端未捕获错误。

目标是以 p50、p95 和失败率区分平台冷启动、凭据服务、Gmail API、APS 与前端渲染瓶颈，而不是仅以单次体感判断。

### 运行时断连恢复

前端不再永久缓存首次失败或已失效的 runtime client。明确的 transport/session 错误会触发单飞重连；带 `retry: "safe"` 的读取调用可在新 client 上重试一次。邮件标签修改、发送、删除等 mutation 只恢复连接并返回本次失败，避免断连后静默重复执行用户操作。

兼容 Runtime 的 heartbeat interval 现在可由 `dispose()` 清理。正式平台优先使用 Anna 注入 SDK，因此 Cloud Agent 进程退出、iframe 重载或 Host 会话回收仍必须通过平台日志确认根因。

### Gmail 外部变更同步

已实现 `sync_inbox_cache`：全量 All-mail 刷新完成后保存 Gmail History cursor；前台 App 每 15 秒在当前邮箱、非 AI 运行且列表空闲时调用只读增量同步。History 事件中的新邮件、删除、已读、标星、归档、重要性和垃圾箱标签变更会合并到 All-mail 缓存，再由前端重新读取缓存快照。

自动刷新间隔是邮箱级设置，可选关闭、15 秒、30 秒、60 秒或 120 秒，默认 15 秒。页面隐藏、AI 执行、列表加载和账户切换期间均暂停调度。

History cursor 过期时不清空旧缓存，而是返回 `resync_required`，前端才执行一次受控全量重建。History 或 metadata 请求失败、缓存写入失败、cursor etag 冲突时均不推进 cursor，下一轮从已确认 cursor 重试。

### 正文与稳定性

邮件详情需要把「缓存命中正文」「Gmail 全量线程请求」「loopback 正文 URL」「前端 HTML 渲染」分别计时并关联请求 ID。断连和闪退需要平台日志确认是否由 Executa 退出、Host iframe 重载、超大 RPC 响应或未处理前端异常触发。
