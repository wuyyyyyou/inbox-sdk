# AI 生产结构优化方案（SQLite 读模型）

状态：调研方案；P0 同步 / P3 Evidence 已在主路径落地（**非** SQLite FTS，见 [邮箱同步 P0](邮箱同步P0缓存优先方案.md) 与 [2.2.7 基线](2.2.7架构与发布基线.md)）  

日期：2026-07-23  

范围：Anna Inbox App 与 Executa 二进制；不引入 PostgreSQL、Redis、云队列、对象存储或常驻外部服务。

多方案对照与取舍过程见：[AI 生产结构多方案选型调研](AI生产结构多方案选型调研.md)。

---

## 1. 已确认目标与约束

### 1.1 产品目标

- 用户请求必须在 **5 秒内返回完整最终答案**，不是仅显示 Thinking、进度或后台 run 已创建。
- 生产场景成功率必须达到 **90% 以上**。
- AI 的定位是邮件助手：搜索、理解、总结、写草稿、整理建议和多轮上下文。
- 邮件写操作继续遵守现有确认机制；AI 不得静默发送、删除、归档或变更标签。

### 1.2 部署约束

- 后端是随 App 发布的 Executa 二进制，而非可新增的常驻服务。
- 允许的新增持久化能力上限为二进制本地维护的 SQLite。
- Gmail 仍是邮件事实源；当前以 APS/local storage 缓存为每邮箱隔离读模型，P3 不引入 SQLite。
- 不采用 PostgreSQL、Redis、Celery、S3、Gmail Watch/PubSub、远程向量库或外部同步服务。
- 现有 `Host Agent Session` 保留为侧栏的产品入口；前端不得恢复散落的业务意图正则路由。

### 1.3 与「AI 优化建议」的对齐与裁剪

| 建议中的能力 | 本方案落地形态 | 原因 |
| --- | --- | --- |
| PostgreSQL + FTS + pgvector | **SQLite + FTS5**（首期不做向量） | 二进制部署、无常驻 DB；失败主因是覆盖/编排 |
| 常驻 Sync / Worker / Queue | **`jobs` 表 + 短预算领取** | 进程可能退出；任务须断点续跑 |
| Gmail Watch / Push | **`history.list` 增量 + 前台轮询** | 已有实现；Watch 依赖外部常驻 |
| Hybrid / Vector Search | 首期不做；结构化 SQL + FTS5 优先 | 126 测例失败与向量无关 |
| Query Plan → SQL → Evidence → LLM | **`query_mail_evidence` 复合工具** | 「找」与「理解」分离 |
| Onyx / Inbox Zero / Mailspring | 借鉴 Pipeline / Rules / 本地 DB，不照搬技术栈 | 详见选型调研文档 |

### 1.4 尚未确认且阻塞上线的前提

当前代码在平台模式下把运行数据写到 `./.data`，仓库无法证明该目录能跨二进制重启、App 更新和平台会话重建持续存在。SQLite 只有在该目录具备上述持久性时，才能作为生产读模型。

**P0 验证必须先完成：**在目标平台写入带随机标识的 SQLite 数据库和 WAL，分别验证二进制重启、App/iframe 重载、平台会话重建及版本升级后均可读取；同时确认每个用户/邮箱的数据目录隔离，且不会被并发二进制实例同时破坏。任一验证失败时，本方案不能承诺 5 秒完整答案或 90% 成功率，应停止 SQLite 主路径改造并回看 [多方案选型调研](AI生产结构多方案选型调研.md) 中的 A/B 备选。

## 2. 现状与问题证据

### 2.1 当前生产路径（App 2.1.6 / Tool 2.2.6）

```text
用户自然语言
  → Host Agent Session（唯一产品入口）
  → query_mail_evidence（Scope Resolver → 一次 QueryPlan → 缓存 Evidence）
  → 精确事实直接模板返回，或 Host 一次最终生成
  → 模型生成
```

`query_mail_evidence` 只读本地全量缓存，不因 UI 的 7/30/60 天显示范围而收窄；`active_scope` 按邮箱和会话持久化，切换线程时重置旧证据指针。Host Session 的 Run 延迟仍受平台模型影响，不能据此承诺 5 秒最终答案。

### 2.2 126 条 APP Tracking

| 指标 | 结果 |
| --- | --- |
| 通过率 | 35.7%（45/126） |
| 平均 / 中位耗时 | 21.7s / ~20s |
| ≤5s 完成 | 4/126 |
| 「暂时不可用」类 | 27 |
| 审核器 JSON 失败 | 25（不得计入产品 KPI） |
| 可靠下界 / 乐观上界 | ~36% / ~56%（均远低于 90%） |

主要技术原因：

1. `search_email` 以实时 Gmail 为主路径，选型 + 搜索 + 读正文 + 再生成尾延迟叠加。
2. 单次最多 20 条摘要；「全部 / 最早 / 没有」无法证明完备。
3. 附件文件名、长线程、联系人事实未统一索引。
4. 多轮草稿 / 引用多为进程内状态，重启不可靠。
5. 缺少结构化覆盖/同步边界事实，模型易编造数据范围话术。

参考：[AI 优化建议](AI优化建议.md)、`tests/APP测试Tracking - INBOX测试-results.md`、[2.2.6 架构与发布基线](2.2.6架构与发布基线.md)。

### 2.3 失败桶 → 本方案能力

| 桶 | 含义 | SQLite 方案落点 |
| --- | --- | --- |
| F1/F9 | 截断、非单调、无完备性 | `sync_state` + COUNT + coverage |
| F2 | 时间窗漏检 | 结构化日期过滤 + 90 天工作集 |
| F3 | 多轮 Gmail 超时 | 本地取证；禁止自由工具环 |
| F4 | 缺附件名 | `attachments` 表 |
| F5 | 多轮/草稿丢失 | `conversation_state` + jobs |
| F7 | 安全规则不足 | 确定性 Rules（与索引解耦可先上） |
| F8 | 边界话术编造 | 代码注入 `boundary` 事实 |
| F10 | 审核器噪声 | 阶段 0 修契约 |

## 3. 设计原则

1. **SQLite 负责找，模型负责理解。** 模型不得把 Gmail 当可无限试探的知识库。
2. **缓存优先、Gmail 受控回源。** 覆盖足够时不得访问 Gmail；缺口才按预算回源一次。
3. **完整性可证明。** 「没有 / 全部 / 最早」必须基于覆盖范围与是否穷尽。
4. **事实与文案分离。** 同步范围、附件、上限、进度由代码提供；模型只解释。
5. **持久任务而非后台幻觉。** 解析/回填记在 `jobs`，invoke 时短预算续跑。
6. **最小数据与最小权限。** 附件字节不入库；按邮箱隔离；日志无正文/query/凭据。

## 4. 目标架构

```text
Gmail
  |
  | 受控首次同步 / history.list 增量 / 缓存缺口回源
  v
Executa 二进制
  |
  +-- SQLite 读模型（每邮箱 mailbox_key 隔离，WAL）
  |     messages / threads / participants / attachments
  |     message_fts（FTS5） / thread_facts / sync_state / jobs
  |     conversation_state
  |
  +-- 预处理器（同步后有限批 jobs）
  |     HTML→text、引用折叠、签名候选、附件清单、事实抽取
  |
  +-- 证据查询器（SQL + FTS + 完备性）
  |     evidence bundle + coverage + boundary
  |
  +-- Host 复合只读工具 query_mail_evidence
  |     一次取证；不足时至多一次受控 Gmail 回源
  v
完整最终答案 / 草稿 / 需确认的操作建议
```

### 4.1 SQLite 并发与生命周期

- 单库多表，业务表含 `mailbox_key`；仅当前 App 用户可访问。
- WAL、外键、有限 `busy_timeout`；单写入协调器；问答用只读/短事务。
- `jobs` 为唯一队列：类型、邮箱、对象版本、状态、尝试次数、下次执行、幂等键。
- Migration 版本化可回滚；失败不破坏现有 JSON/APS 缓存。
- 禁止入库：附件字节、完整 MIME、token、凭据、无限长正文。

### 4.2 最小表模型

| 表 | 关键内容 | 用途 |
| --- | --- | --- |
| `sync_state` | history_id、覆盖起止、最后成功同步、状态 | 是否足够回答 |
| `messages` | message/thread id、日期、参与人、主题、labels、正文文本版本 | 结构化过滤 |
| `message_fts` | subject、清洗正文、参与人、附件文件名 | 中英全文 |
| `threads` | 最新版本、参与人、短摘要、状态、待办版本 | 长线程快答 |
| `attachments` | 文件名、MIME、大小、解析状态、截断文本/错误码 | 附件取证 |
| `thread_facts` | 金额、会议、联系人、截止日期、来源 message id、置信度 | 事实快路径 |
| `conversation_state` | 当前线程、证据集、草稿、选择项、批进度、过期 | 多轮 |
| `jobs` | 同步、清洗、事实、附件、摘要 | 断点续跑 |

首期唯一全文方案为 FTS5；向量不进入首期。

## 5. 同步与预处理

### 5.1 同步策略

1. 首次同步近期工作集：默认最近 **90 天** metadata + 正文纯文本 + 附件清单；更早历史按 jobs 倒序回填。
2. `history.list` 增量；**SQLite 提交成功后再推进** `history_id`。
3. 无常驻循环：前台打开、列表刷新、AI 前短检查、启动时领取有限任务。
4. 回源仅：首次覆盖、缺口、显式刷新、History 过期重建；失败保留旧索引与覆盖状态。
5. 可从现有 All-mail 缓存导入起步；AI 判定以 SQLite `sync_state` 为准。

### 5.2 预处理

- 安全清洗后 HTML→搜索纯文本；保留 message 段落边界。
- 引用/签名保守折叠；不可靠则不写入事实。
- 同步写附件元数据；PDF/Office/图片仅建解析 job；MIME/大小/耗时白名单。
- 事实带 source message id 与置信度；高风险字段回答前复核原文证据。
- 线程摘要仅在版本变化后重算。

## 6. 查询与回答路径

### 6.1 复合取证工具 `query_mail_evidence`

Host 接收自然语言，内部在 SQLite 完成：

1. 结构化过滤（日期、参与人、标签、附件、线程、选择项）
2. FTS5 候选与线程合并
3. 「全部/最早/没有」的 COUNT 与完备性检查
4. `thread_facts` / 附件 / 摘要补字段
5. 返回 budget 内 evidence bundle：引用 id、片段、覆盖、新鲜度、是否完整、是否需回源

仅证据不足时允许 **一次** 受时间预算的 Gmail 回源；仍不足则返回可解释不足状态。禁止 Host 自由多轮 search/read 环。

### 6.2 快路径

| 请求类型 | 取证 | 完整答案 |
| --- | --- | --- |
| 数量、日期、联系人、附件名、会议、已知金额 | SQL / facts / FTS | 模板化 + 引用 |
| 关键词定位 | FTS + 过滤 | 模板；必要时一次模型压缩 |
| 长线程/待办/关系 | 摘要 + 最近消息 + 命中段 | 一次模型，不再调工具 |
| 草稿/改写 | 线程证据 + conversation_state | 一次模型；草稿为待审 artifact |
| 覆盖不足/附件未解析 | 任务状态 + 一次回源 | 明确失败/范围不足，不编造 |

### 6.3 多轮与边界事实

- `conversation_state` 持久化 thread、证据、草稿、选择、批进度；过期或版本变化须澄清。
- 每次回答可附 `boundary`：`coverage_*`、`result_complete`、`truncated`、`data_path`（`sqlite_index` | `gmail_live_fallback` | `insufficient`）。
- 模型只复述代码注入的边界事实，禁止编造同步机制。

## 7. 性能与可靠性

### 7.1 端到端 5s 预算（p95）

| 阶段 | 预算 |
| --- | --- |
| 前端提交、调度、认证 | 0.4s |
| SQLite 查询/FTS/组装 | 0.6s |
| 模板化事实回答 | 0.3s |
| 单次模型生成 | 3.0s |
| 前端渲染与余量 | 0.7s |
| 合计 | 5.0s |

模型 p95 若 >3s，须扩大模板化/预计算或调整 SLA；不能单靠 SQLite 消除模型尾延迟。

### 7.2 成功率定义

1. 5s 内完整最终文本或草稿 artifact  
2. 真实引用或明确覆盖/不可用说明  
3. 不编造事实与机制  
4. 写操作仅确认卡片  

按场景、邮箱、冷/热索引分别统计；审核器失败单独记账。

## 8. 实施顺序与门槛

### 阶段 0：验证与基线

- 平台 SQLite 持久性 / WAL / 隔离 / 并发探针  
- 审核器契约修复；G30 黄金子集  
- request_id 安全分段耗时（Host / Gmail / 模型）  

**门槛：** 重启后可读同一库；126/G30 可审计基线。

### 阶段 1：读模型与同步

- 版本化 schema + 迁移  
- 从现有缓存导入；History 写 SQLite；jobs 续跑  
- JSON/APS 保留回退  

**门槛：** 90 天可恢复；失败不推进 cursor；无跨邮箱读。

### 阶段 2：FTS 与确定性取证

- FTS5 + `query_mail_evidence`  
- 覆盖：账单、会议、联系人、日期、退信、最早/全部、附件名、窗口单调  

**门槛：** 热索引事实查询 p95 ≤2s；答案可追溯证据。

### 阶段 3：Host 收敛与 5s 完整回答

- 侧栏一次复合取证；模板事实 + 一次模型  
- 确定性错误语义；Rules + boundary  

**门槛：** 审核噪声清零后成功率 ≥90%；完整答案 p95 ≤5s；P0 单独达标。

### 阶段 4：派生事实、附件、多轮

- thread_facts / 待办 / 受限附件解析  
- conversation / 批处理 / 草稿持久化  

**门槛：** 重启与多轮不丢上下文。

## 9. 风险与明确不做

| 风险 | 控制 |
| --- | --- |
| 本地盘不持久 | 阶段 0 阻塞；失败则改选型调研中的 A/B |
| 并发锁 | WAL、单写、短事务、busy_timeout |
| 半同步「没有」 | 缺覆盖不作否定结论 |
| 外部尾延迟 | 本地优先、一次回源、模板化 |
| 附件安全 | MIME 白名单、大小/耗时、无二进制入库 |
| Prompt injection | 正文非可信；mutation 确认 |
| 存储膨胀 | 文本限额、配额、清理 |

**首期不做：** 向量库、Embedding、全量附件二进制、外部队列、Gmail Push Watch、前端业务正则路由、未确认 mutation。

## 11. 最终决策

采用「**本地 SQLite 邮件读模型 + FTS5 + 持久 jobs + 单次证据工具 + 边界事实 + Host Agent 生成**」。

能否兑现 5s / 90%：**先**平台 SQLite 持久性，**再**模型 p95 ≤3s，**再**索引覆盖与诚实评测。阶段 0 未过不得对外承诺。
