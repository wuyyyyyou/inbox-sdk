# 联系人记忆架构设计

## 目标

联系人记忆用于补足当前 Gmail thread 之外的上下文。它不是事件日志，也不是当前 thread 的重复摘要，而是 mailbox-scoped、contact-scoped、thread-indexed 的长期摘要文件。

核心目标：

- 同一个联系人在不同 mailbox 下严格隔离。
- 每个联系人一个记忆文件。
- 每个记忆条目对应一个 Gmail thread。
- 每个 thread 记忆包含完整 thread 总结和逐封邮件摘要。
- 召回时硬排除当前 thread，只召回同联系人其他 thread 的记忆。
- 召回相关性由 LLM selector 判断，不用规则打分。

## 存储选择

正式环境使用 APS。本地开发使用 local JSON，它们共用同一 storage abstraction。

Anna session history 不作为联系人记忆主存储。session 适合单次运行上下文，不适合长期、可删除、可重建、按 mailbox/contact/thread 索引的联系人记忆。

## 隔离边界

联系人记忆必须按 mailbox 隔离。同一个 `contact_email` 在不同 mailbox 下不能共享记忆。

存储 key：

```text
mailbox/{normalized_mailbox}/contacts/{normalized_contact}/memory
```

所有 source refs 都必须带 mailbox：

```json
{
  "mailbox": "hr@anna.partners",
  "thread_id": "...",
  "message_id": "...",
  "date": "2026-06-07T..."
}
```

## 记忆文件结构

```json
{
  "mailbox": "hr@anna.partners",
  "contact_email": "alice@example.com",
  "display_name": "Alice",
  "threads": [
    {
      "thread_id": "...",
      "subject": "Priya next round",
      "thread_summary": {
        "summary": "Alice and the user discussed whether Priya should move to the next interview round.",
        "current_state": "Alice is waiting for the user's decision.",
        "open_loop": "Decide whether to advance Priya.",
        "status": "open",
        "importance": "medium"
      },
      "message_summaries": [
        {
          "message_id": "...",
          "from": "alice@example.com",
          "direction": "inbound",
          "date": "2026-06-07T...",
          "summary": "Alice asked whether Priya should move forward faster.",
          "action_signal": "asks_for_decision"
        }
      ],
      "source_refs": [],
      "updated_at": "2026-06-07T..."
    }
  ],
  "created_at": "...",
  "updated_at": "..."
}
```

状态只保留四种：

```text
open              对方在等用户
waiting_for_them  用户已回复，等对方
closed            已处理完
unknown           不确定
```

## 写入原则

联系人记忆基于 mailbox observation，而不是只基于 app 内操作。

写入来源：

- Brief 扫描到的重要 thread。
- 最终生成 card 的 thread。
- Brief 判断为重要候选但未必展示成 card 的 thread。
- 最新邮件来自用户本人、因此被过滤不生成 card 的 thread。
- 用户在 app 内回复后的回复内容。
- 未来历史补取也写入同一个 thread entry。

写入方式：

```text
Brief scan / app reply / owner-replied observation
  -> build thread memory update input
  -> LLM summarizes thread + per-message summaries
  -> upsert contact memory file by mailbox/contact/thread_id
```

LLM 只负责生成当前 thread entry 的摘要，不直接维护整个联系人文件。代码负责 upsert、去重、限长和落库。

## Thread 记忆更新

每次扫到某个 thread，更新该联系人的该 thread entry：

- 如果 thread entry 不存在，新建。
- 如果存在，重写 `thread_summary`。
- 对每封邮件按 `message_id` upsert `message_summaries`。
- 如果观察到用户回复，写入 outbound message summary，并更新 status。
- 如果最新邮件来自用户本人，status 可变为 `waiting_for_them` 或 `closed`。

更新 prompt 输入：

```json
{
  "contact_email": "alice@example.com",
  "thread_id": "...",
  "subject": "...",
  "existing_thread_memory": {},
  "thread_messages": [
    {"message_id": "...", "from": "...", "date": "...", "body": "..."}
  ],
  "user_reply": "optional app reply or latest owner email"
}
```

输出：

```json
{
  "thread_summary": {
    "summary": "Alice asked whether Priya should move to the next round faster.",
    "current_state": "The user needs to decide whether to advance Priya.",
    "open_loop": "Decide whether to advance Priya.",
    "status": "open",
    "importance": "medium"
  },
  "message_summaries": [
    {
      "message_id": "...",
      "from": "alice@example.com",
      "direction": "inbound",
      "date": "...",
      "summary": "Alice asked whether Priya should move forward faster.",
      "action_signal": "asks_for_decision"
    }
  ]
}
```

## 召回原则

召回不做规则打分，直接使用 LLM selector。规则只做硬约束：

- same mailbox
- same contact
- exclude current thread
- 候选数量截断
- 空记忆过滤

召回流程：

```text
1. load contact memory file
2. filter hard constraints
3. build compact candidate list
4. call LLM selector
5. load selected thread memory details
6. compact into prompt context
```

Selector 输入：

```json
{
  "purpose": "card_generation | draft_generation | thread_summary",
  "current": {
    "thread_id": "current_thread",
    "subject": "Can we move faster?",
    "latest_body": "Can we move faster on Priya?",
    "sender": "alice@example.com",
    "message_count": 1
  },
  "candidate_memories": [
    {
      "thread_id": "old_thread_1",
      "subject": "Priya next round",
      "summary": "Alice and the user discussed whether Priya should move to the next interview round.",
      "current_state": "Alice is waiting for the user's decision.",
      "open_loop": "Decide whether to advance Priya.",
      "status": "open",
      "recent_messages": [
        "Alice said Priya interviewed well.",
        "User asked for more details before deciding."
      ]
    }
  ]
}
```

Selector 输出：

```json
{
  "selected": [
    {
      "thread_id": "old_thread_1",
      "relevance": "high",
      "reason": "The current email mentions Priya and moving faster, matching the prior Priya next-round discussion.",
      "include_message_ids": ["msg_1", "msg_2"]
    }
  ],
  "none_reason": ""
}
```

Selector 规则：

- 不要因为同一个联系人就选择记忆。
- 不要选择当前 thread。
- 只有同一个人、项目、决策、请求或 open loop 才选择。
- 不确定就返回空。
- `draft_generation` 优先选择包含用户过去决定或回复立场的记忆。
- `thread_summary` 优先选择能解释当前 thread 缺失上下文的记忆。
- `card_generation` 优先选择会改变重要性、紧急性或推荐动作的记忆。

## 注入 Prompt 的内容

选中后不把整个 thread memory 塞入 prompt，只注入 compact context：

```text
Related contact memory:
- Priya next-round discussion: Alice and the user discussed whether Priya should advance. Current state: waiting for the user's decision.
- Prior user reply: User asked for more details before deciding.
```

如果 selector 指定了 `include_message_ids`，可以补充对应 per-message summaries。

## 对 Cards 的影响

Cards 生成读取同联系人其他 thread memory，只作为判断上下文，不扩大 card 三行文案。

目标：

- 判断当前邮件是否承接旧事项。
- 让 title/summary/recommendation 更具体。
- 不把历史细节堆进 UI。

## 对 Draft 的影响

Draft 生成读取同联系人其他 thread memory，尤其是：

- 旧 thread 的 `current_state`
- 用户过去 outbound message summary
- open loop
- reply guidance

低置信或无关记忆不注入 draft。

## 对 Thread Summarize 的影响

Thread summarize 拆成两个概念：

- 当前 thread summary：只总结当前 thread。
- Related context：只来自同联系人其他 thread memory。

单封短邮件：

- 没有 related context：不显示 summary 模块。
- 有 related context：显示 Related context，不重复总结原文。

多轮 thread：

- 显示当前 thread summary。
- 如果召回到其他 thread memory，再补充 Related context。

## 隐私与维护

必须支持后续删除能力：

- 删除某 mailbox 下某联系人记忆。
- 删除某 mailbox 的全部联系人记忆。
- 未来如有全局索引，单独删除全局索引。

记忆必须保留 source refs，错误记忆可以回溯和重建。
