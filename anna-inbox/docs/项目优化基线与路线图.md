## 2. 项目当前心智模型

### 2.1 产品概念

- `Mailbox`：一个被 Anna Inbox 读取和处理的 Gmail 邮箱账户。
- `Brief`：稳定、可预测的邮箱扫描工作流，产出 Attention Cards。
- `Ask`：用户自然语言驱动的开放式邮箱查询，输出结构化答案，不等同于 Brief。
- `Custom Scan Plan`：Ask 的可复用查询计划，不是 Brief 的 Scan Plan。
- `Scan Plan`：Mailbox 的 Brief 扫描偏好，包括扫描窗口和最大扫描量。
- `Attention Card`：Brief 产出的可处理邮件事项。
- `Cleanup Bundle`：Brief 聚合低价值邮件的一张折叠卡片。
- `Handle`：用户处理单张 Attention Card 的详情体验。

### 2.2 代码结构

  app.json                      # App metadata

    features/ask/               # Ask 视图

## 3. 必须遵守的硬约束

### 3.1 Executa / 协议

- JSON-RPC 2.0 over stdio，每行一条 JSON 消息。
- `stdout` 只能输出协议响应；日志、调试、异常诊断写 `stderr`。
- 消息使用 UTF-8。
- 工具凭据通过 manifest `credentials` 声明，通过 `params.context.credentials` 或环境变量接收。
- 不要新增接收 OAuth token、access token、refresh token、API key 的工具参数。
- 大内容不要通过 JSON-RPC result 返回；大文件或二进制 artifact 使用 APS files/object storage 或轻量引用。

### 3.2 存储

- 存储统一走 `mail_agent/storage/ops.py`，不要在业务调用方散落直接访问 APS/local client。
- 读取 KV 时用 `result.get("exists")` 判断是否存在；`null`、`false`、`0`、`[]` 可能是合法值。
- Mailbox 级 key 使用 `mailbox/<sanitized-mailbox>/...` 隔离。
- `scan_state`、run history、cards、preferences、custom plans、summaries、drafts 属于小 JSON。
- 大 blob、长 HTML、图片、PDF、大数组不要塞进 APS KV。

### 3.3 Gmail / 隐私

- Gmail 凭据只能来自 Anna platform authorization、插件凭据、环境变量或本地 token 文件。
- 不记录 OAuth token、access token、refresh token、API key、完整 authorization header 或 credential context。
- mark-read、trash、send 等 Gmail 状态变更必须保持 guardrail，默认 dry run 或明确用户操作。

### 3.4 前端

- 前端源码根目录是 `anna-inbox/src/`。
- 技术栈保持 Vite + React + TypeScript。
- 工具调用集中在 `src/api/mailAgentClient.ts`，组件不要直接写 Executa tool 名。
- `npm run build` 必须先 typecheck，再 Vite build。
- `bundle/` 是构建产物，不手写维护，不提交。
- 修改卡片字段时必须对照 `cards/service.py::cards_to_frontend`、`storage/types.py::PersistentCard` 和前端 DTO。

### 3.5 多邮箱边界

- 所有卡片操作必须以 `card.details.mailbox` 为准，不依赖全局 `state.mailbox`。
- Contact Memory 按 mailbox 严格隔离。
- Scan Plan 按 mailbox 独立存储。
- Brief 扫描只处理 Sources 中勾选的邮箱。
- Ask 的目标邮箱需要在 UI 和后端参数中保持清晰，避免“显示多邮箱、实际只扫第一个”的错觉。

## 4. 已发现的文档/代码偏差

### 4.1 协议参考缺失

`AGENTS.md` 要求修改协议、存储、凭据或 Executa 启动行为前阅读：

- `anna-inbox/.docs/anna-rpc/...`
- `anna-inbox/.docs/anna-storate/...`

但当前工作树未包含 `anna-inbox/.docs/`，且 `.gitignore` 忽略 `**/.docs`。后续如果要修改协议/APS/授权/启动行为，必须先补齐或确认这些协议参考。

### 4.2 版本号不一致

当前观察到：

- `inbox-tool/src/pyproject.toml`：`1.0.5`
- `inbox-tool/manifest.json`：`1.0.1`
- `inbox-tool/executa.json`：`1.0.1`
- `anna-inbox/executas/inbox-tool/executa.json`：`1.0.1`
- `anna-inbox/manifest.json` required executa min version：`1.0.1`
- `AGENTS.md` 写“当前 Executa 版本是 `1.0.2`”

如果涉及发布、打包、identity sync、required executa 版本，应先统一版本来源，再运行 `scripts/sync/sync_executa_identity.py --check`。

### 4.3 当前 UI Brief 路径与老 pipeline 首次/增量逻辑不完全一致

老路径 `mail_agent/core/pipeline.py::run_mail_task` 会读取 `ScanState.total_scans`：

- 首次扫描：不传 `after_timestamp`
- 非首次扫描：传 `last_message_internal_date`，Gmail query 加 `after:`

当前前端主路径走 `anna_inbox_executa/brief_flow.py::_brief_prepare_scan`，调用 `run_mail_scan(mailbox, configured_max, newer_than_days=scan_window_days)`，没有使用 `after_timestamp`。因此当前 UI 路径主要依靠：

- Gmail `newer_than:<N>d` 窗口
- processed message index 去重
- thread dedup

后续优化扫描增量逻辑时，应先决定是否把 `last_message_internal_date` 逻辑迁入短 invoke 状态机。

### 4.4 HTML 邮件正文清洗未落地

`anna-inbox/docs/HTML邮件处理方案.md` 仍标注“待确认实施进度”。当前 `mail_agent/mail_providers/gmail/adapter.py::_decode_body()`：

- 收集 `text/plain` 和 `text/html`
- 当前优先返回 `html_parts`
- 不做 HTML to text / Markdown 清洗

这会影响 LLM token 成本和正文判断质量，是后续高 ROI 优化点。

### 4.5 测试说明已更新但 AGENTS 未完全同步

`AGENTS.md` 只列了两个 Python 脚本测试，但当前已有更多测试：

## 5. 优化优先级

### P0：基线校准和低风险保护

目标：先降低“改错地方”的风险。

- 统一 Executa 版本号和身份同步规则。
- 明确哪些 manifest 是单一来源，哪些是同步产物。
- 补一份当前测试矩阵到项目文档或 README。
- 确认 `anna-inbox/.docs/` 协议参考是否应恢复到本地。
- 检查 smoke test 输出是否仍是合法 newline-delimited JSON。

验收：

- `scripts/sync/sync_executa_identity.py --check` 通过，或明确记录为什么暂不通过。
- `describe` / `health` smoke test 通过。
- 无凭据、token、cache、bundle 等生成物被提交。

### P1：Gmail 扫描和正文质量优化

目标：提升 Brief/Ask 的输入质量和扫描行为可解释性。

建议子项：

1. HTML 邮件正文清洗
   - 优先 `text/plain` 的有效内容。
   - HTML-only 邮件转为干净文本或 Markdown。
   - 至少提供 regex fallback，避免新增硬依赖。
   - 给 `_decode_body()` 加脚本式单元测试。

2. 短 invoke Brief 增量扫描对齐
   - 在 `_brief_prepare_scan` 中读取 `ScanState`。
   - 非首次扫描考虑传 `after_timestamp=last_message_internal_date`。
   - 保留 processed-message 过滤作为第二层防重。
   - 注意 Gmail thread 查询 `after:` 与 thread 内旧消息窗口的交互。

3. Scan Plan 字段消费确认
   - 当前 `ScanPlan` 实际字段是 `scan_window_days/max_messages/scan_categories`。
   - manifest / 前端可能暴露了更多旧字段，需梳理字段映射。
   - 前端文案必须把 `max_messages` 表达为“最多邮件数”，不能再写成 Max threads。
- Brief 扫描入口必须把 `max_messages` 当作硬上限：用户设置 50，就最多进入后续管线 50 封邮件。
- `scan_window_days` 必须同时作用于 Gmail query 和本地 cache fallback，不能只作为 UI 展示值。
- 首次扫描必须覆盖扫描窗口内的已读和未读邮件，不能默认加 `is:unread`；否则用户容易漏掉已经打开但未处理的邮件。

验收：

- `test_scan_window.py` 覆盖 query 构造和 fallback window。
- HTML 清洗测试覆盖 plain-only、html-only、plain+html、无依赖 fallback。
- Brief smoke path 不改变工具契约。
- 前端启动扫描时按 mailbox 读取当前 Scan Plan，并把 `max_messages` / `scan_window_days` 的实际值带入 run 参数或后端存储读取路径。
- 后端 `run_mail_scan()` 返回的 `MessageLite` 数量不得超过 `max_messages`。

### P2：卡片和状态一致性

目标：减少重复卡、过期卡和跨邮箱误操作。

建议子项：

- 检查 active cards 外部处理感知：用户已在 Gmail 回复后，App 卡片是否可自动 dismiss 或降级。
- 后端补充卡片操作兜底校验：
  - `card_id` 必须存在于传入 mailbox 的 active cards。
  - `message_id/thread_id` 应能在对应 mailbox 缓存或 Gmail 结果中找到。
- 聚合卡片排序从 “priority + created_at” 扩展到更稳定的多字段排序：
  - pending 优先
  - priority 优先
  - 最近邮件时间或更新时间优先
  - mailbox 作为 tie-breaker
- `snooze/learning` 偏好逐步改为 mailbox scoped，避免多邮箱污染。

验收：

- storage integration 覆盖卡片合并、按邮箱隔离、状态更新。
- 前端 helper 测试覆盖分类、可见性、mailbox key。

### P3：Ask 多邮箱和检索质量

目标：让 Ask 的目标范围清晰，提升召回和回答稳定性。

建议子项：

- UI 明确展示 Ask 目标邮箱。
- 后端 Ask 接受 `mailboxes: list[str]` 或明确只接受单 mailbox。
- Ask result item 必须带 `mailbox`，Mark read / Trash / Reply 使用 item mailbox。
- 继续完善 structured Ask planner：
  - LLM 不直接写脆弱 Gmail 语法。
  - 代码负责构造 query 和自适应放宽。
  - 联系人记忆可用于 people resolution。

验收：

- `test_ask_planner.py`
- `test_ask_search.py`
- `test_ask_answer.py`
- 前端 Ask 操作不会回落到全局 `state.mailbox`。

### P4：测试、文档和可维护性

目标：让后续迭代可持续。

建议子项：

- 将关键测试命令更新进 README 或单独测试文档。
- 为 Phase 1/Phase 2 解析、guards、cards_to_frontend 增加 focused tests。
- 为 frontend DTO adapter / run status helpers 保持 Vitest 覆盖。
- 清理过期文档中的旧路径、旧版本号、旧 tool id。
- 对长文件做局部整理，但避免一次大重构同时碰前端、管线、协议入口。

验收：

- Python 脚本测试和 frontend Vitest 可按模块独立运行。
- 修改协议或工具契约时附带 describe smoke。
- 修改前端源码时 `npm run build` 通过。

## 6. 每次优化的工作模板

每次开始具体优化前，按以下顺序执行：

1. 定义范围
   - 只改一个明确主题。
   - 写清楚涉及 Brief、Ask、Storage、Gmail、Frontend 哪些边界。

2. 补读相关文档
   - Brief：`Brief管线全链路设计.md`、`Brief可续跑短Invoke状态机改造方案.md`
   - Ask：`Ask-重设计计划.md`、`Ask链路重构方案.md`、`Ask-Planner线程感知优化.md`
   - 多邮箱：`多邮箱接入方案.md`
   - 存储：`本地持久化统一改造.md`
   - 联系人记忆：`联系人记忆架构设计.md`
   - HTML：`HTML邮件处理方案.md`
   - 打包：`PyInstaller二进制打包指南.md`

3. 定位真实入口
   - 不只看旧 pipeline，确认当前前端实际调用路径。
   - 对照 manifest、dispatcher、mailAgentClient。

4. 小步改动
   - 优先局部函数或单一模块。
   - 不顺手重设计 UI、协议、存储 schema。
   - 不写入 token、cache、bundle、release artifact。

5. 验证
   - 按第 7 节测试矩阵选择。
   - 如果依赖 Gmail、Anna platform、APS、LLM sampling，说明它不是无条件可用。

6. 记录结果
   - 说明改了什么、为什么、跑了哪些测试、剩余风险。

## 8. 优先推荐的第一批优化候选

### 8.1 HTML 正文清洗

原因：

- 当前实现优先返回原始 HTML。
- 对 Brief Phase 2、Ask Answer、Draft、Thread Summary 都会造成 token 浪费和内容噪音。
- 可局部修改 Gmail adapter，并用纯函数测试覆盖。

建议范围：

- 修改 `mail_agent/mail_providers/gmail/adapter.py::_decode_body()`。
- 新增内部 helper：
  - `_decode_part_data`
  - `_html_to_text`
  - `_strip_html_tags_regex`
  - 可选 `_strip_quoted_reply`
- 不引入硬依赖；如果使用 `html2text/bs4`，必须 graceful fallback。

### 8.2 Brief 短 invoke 增量扫描对齐

原因：

- 老 pipeline 有 `is_first_scan` + `after_timestamp`。
- 当前 UI 主路径没有使用 `after_timestamp`。
- 继续只依赖 `newer_than` + processed index 会重复查最近窗口内大量 thread。

建议范围：

- 在 `_brief_prepare_scan` 读取 `get_scan_state(mailbox)`。
- 若 `total_scans > 0` 且有 `last_message_internal_date`，传给 `run_mail_scan`。
- 保留 processed-message filter。
- 增加或扩展 `test_scan_window.py` 覆盖 `after:` query。

### 8.3 版本与身份同步

原因：

- 当前版本信息不一致。
- 发布/打包/manifest 相关改动容易引入安装和工具调用问题。

建议范围：

- 确认目标版本。
- 更新 `inbox-tool/manifest.json`。
- 运行 `python scripts/sync/sync_executa_identity.py --check` 或实际同步。
- 对齐 `pyproject.toml` 是否需要使用同一版本策略。

### 8.4 Brief Scan 设置严格执行

原因：

- Sources 抽屉目前把扫描量写成 `Max threads`，但用户理解的是“最多取多少封邮件”。
- 后端 `run_mail_scan(mailbox, max_threads, ...)` 当前按 thread 停止扫描；一个 thread 内多封邮件会让实际进入 Brief 的邮件数超过用户设置。
- 前端启动 Brief 时仍传固定 `max_messages: 50`，容易让 UI 设置和实际扫描参数看起来不一致。
- `scan_categories` 当前主要是持久化字段，尚未进入 Gmail query 过滤；继续展示会造成“选择了分类就严格只扫这些分类”的错觉。

建议范围：

- 前端 Sources 抽屉只保留当前已经严格执行的两个设置：`Scan window` 和 `Max emails`。
- `Max emails` 的 preset 保留 50 / 100 / 150，自定义范围保守限制在 10-500；保存前做整数 clamp。
- `startScan` 对每个 mailbox 读取当前 Scan Plan，并把 `max_messages` 同步传给 `start_mail_agent_run` / `continue_mail_agent_run`，避免固定 50 的旧参数继续误导。
- 后端 `run_mail_scan()` 保留函数签名兼容，但把第二个参数解释为 message hard limit：返回给后续 Phase 1/Phase 2 的 `MessageLite` 数量必须 `<= max_messages`。
- 首次扫描 query 只受时间窗口、聊天排除和数量上限约束，不加 unread/read 状态过滤；增量扫描再叠加 `after_timestamp` 和 processed index。
- 进度字段同时返回 `messages_fetched`、`max_messages`，旧的 `max_threads` 仅作为兼容字段，不再作为 UI 文案来源。

验收：

- `uv run python tests/test_scan_window.py` 增加 “同一 thread 多封邮件也不超过 max_messages” 回归测试。
- `uv run python tests/test_brief_incremental_scan.py` 确认短 invoke 仍读取 Scan Plan 的窗口和数量。
- `cd anna-inbox && npm run build` 确认前端类型和构建通过。
