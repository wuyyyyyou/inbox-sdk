# 附件下载与外部链接打开方案

> 状态：已按调整方案实施。真实附件下载依赖 Anna Files/APS 能力；local stub 下会给出不可用提示。  
> 日期：2026-06-24  
> 适用范围：Anna Inbox 前端 Handle 视图、Gmail adapter、Executa tool contract、APS/Host 文件下载能力。

## 1. 背景与目标

用户反馈：有附件、有链接的邮件确实需要处理，最好能直接下载或打开。

目标体验：

- 邮件存在附件时，在 Brief 卡片上以紧凑 chip 展示附件文件名，空间不足时展示首个附件 + `+N` 或附件数量。
- 邮件存在附件时，Handle 页在原文未展开前提示用户点击 `Show full email` 后下载附件；展开原文后显示附件下载列表。
- 邮件存在外部链接时，不再额外展示独立 `Links` 区块；只保留原邮件正文内链接点击，并确保它在 Anna App 外的新标签页/系统浏览器打开，不在工具 WebView 内直接跳转。
- 附件正文、图片、PDF 等大内容不通过 JSON-RPC result 返回，只返回轻量元数据或短期下载引用。
- 不新增接收 Gmail/OAuth token 的工具参数；下载仍使用 Executa 内部既有凭据来源。

非目标：

- 本方案不做 Gmail 附件预览器。
- 不自动下载所有附件。
- 不在 Brief 列表阶段读取附件字节。
- 不修改 Gmail 邮件状态。
- 不在 Handle 页额外展示结构化 Links 列表，避免信息重复和占用详情页空间。

## 3. 推荐方案概览

采用“详情加载元数据，点击后准备下载”的两段式方案。

```text
Brief scan
  -> 只保留 has_attachment / 轻量摘要

用户打开 Handle
  -> get_card_detail 返回附件元数据
  -> 未展开原文时提示 Show full email 后可下载附件
  -> 展开原文后渲染附件 Download 按钮

用户点击 Download
  -> prepare_attachment_download 单独取 Gmail attachment bytes
  -> 上传到 APS Files / Host transient file
  -> 返回短期 download_url
  -> 前端用 <a download target="_blank"> 触发下载

用户点击链接
  -> 只在原邮件正文内点击 <a href target="_blank" rel="noopener noreferrer">
  -> 新标签页/系统浏览器打开
```

核心原则：

- 卡片列表只展示附件名称/数量，不下载附件。
- 卡片详情只返回附件和链接元数据，不返回附件字节。
- 附件下载必须由用户点击触发。
- 链接点击必须脱离工具内页面导航。
- 不再展示独立 Links 面板；链接信息留在原邮件正文语境中。

## 4. 数据契约草案

### 4.1 卡片与 CardDetailPayload 扩展

在 `FrontendCard` 和 `get_card_detail` 返回中增加附件轻量字段：

```ts
interface MailAttachmentMeta {
  id: string;              // 前端稳定 key，建议 message_id + part index/hash
  message_id: string;
  filename: string;
  mime_type: string;
  size: number;
  source: "gmail";
  downloadable: boolean;
}

interface MailExternalLink {
  id: string;
  url: string;
  text: string;
  host: string;
  source: "html" | "text";
}

interface CardDetailPayload {
  card?: FrontendCard;
  thread_context?: Record<string, unknown>;
  contact_context?: Record<string, unknown>;
  latest_body?: string;
  latest_body_html?: string;
  body_loaded?: boolean;
  attachments?: MailAttachmentMeta[];
}
```

说明：

- `attachmentId` 不直接暴露给前端作为长期 ID。后端可用 `id` 映射回 `message_id + attachmentId`，或在点击下载时重新读取缓存并校验。
- `attachments` 是小 JSON，可随详情返回。
- Brief 卡片也可携带同一 `attachments` 字段，用于展示首个文件名和数量。
- 链接不作为当前前端 DTO 的一等展示字段；当前只保留原文 HTML 内链接点击兜底。

### 4.2 新增工具草案：prepare_attachment_download

新增 Executa tool：

```json
{
  "name": "prepare_attachment_download",
  "description": "Prepare a short-lived download URL for a Gmail attachment behind a card.",
  "parameters": [
    {"name": "mailbox", "type": "string", "required": true},
    {"name": "card_id", "type": "string", "required": true},
    {"name": "attachment_id", "type": "string", "required": true}
  ],
  "timeout": 120
}
```

返回：

```json
{
  "ok": true,
  "filename": "offer.pdf",
  "mime_type": "application/pdf",
  "size": 235812,
  "download_url": "https://...",
  "expires_at": "2026-06-24T12:00:00Z"
}
```

安全校验：

- `mailbox` 必须非空。
- `card_id` 必须存在于该 mailbox 的 active cards。
- `attachment_id` 必须能在该 card 对应的 Gmail message/thread 附件元数据中找到。
- Gmail 凭据仍通过既有 credentials/context/local token 获取，不作为参数传入。
- 日志不得记录 access token、authorization header、完整 credential context。

## 5. 附件下载实现路径

### 5.1 APS/Host 文件路径（推荐）

1. 用户点击附件 `Download`。
2. 前端调用 `prepare_attachment_download(mailbox, card_id, attachment_id)`。
3. Executa 使用 Gmail API 读取附件：

   ```text
   GET /gmail/v1/users/me/messages/{message_id}/attachments/{attachmentId}
   ```

4. 后端 base64url 解码 Gmail 返回的 `data`。
5. 将字节写入 APS Files 或 Host transient upload，得到短期 `download_url`。
6. 工具只返回短期 URL 和元数据。
7. 前端创建临时 `<a href download target="_blank" rel="noopener noreferrer">` 并触发下载。

需要确认项：

- 当前 `FilesClient.download_url()` 方法存在，但 app/executa manifest 尚未显式声明 APS files capability；实施前需补读协议参考或确认 Anna Host 实际 capability 名。
- 如果改 manifest host capabilities，需要同步 `inbox-tool/manifest.json`、`anna-inbox/executas/inbox-tool/executa.json`、`anna-inbox/manifest.json`，并跑 describe smoke。

### 5.2 本地开发 fallback

由于当前 local FilesClient 是 stub，本地开发有两种可选策略：

策略 A（推荐 MVP）：本地无 files 能力时禁用真实下载，按钮显示错误提示：

```text
Attachment download requires Anna Files storage in this runtime.
```

优点：不违反“大内容不走 JSON-RPC”的硬约束，行为最保守。

策略 B（仅限小附件调试）：对小于 1MB 的附件返回 `content_b64`，前端生成 Blob 下载。

风险：容易被误用到大文件；需要严格大小上限、测试覆盖和明确注释。除非本地调试强依赖，建议不作为第一阶段实现。

## 6. 外部链接打开实现路径

### 6.1 HTML 正文中的链接

后端继续在 HTML 清洗阶段保证：

```html
<a href="https://example.com" target="_blank" rel="noopener noreferrer">
```

前端在 DOMPurify 后额外做一次事件兜底：

- 捕获 `.original-body-html a[href]` 的点击。
- `preventDefault()`。
- 只允许 `http:`、`https:`、`mailto:`。
- 调用 `window.open(url, "_blank", "noopener,noreferrer")`。
- 如果 `window.open` 失败，降级为临时 `<a target="_blank">` 点击。

这样即使邮件 HTML 缺少 `target`，或 DOMPurify/宿主环境改变了属性，也能保证不在工具内部导航。

### 6.2 不展示结构化 Links 列表

取消独立 Links 面板。原因：

- 详情页中的 Links 区块会重复原邮件正文里的上下文。
- 多个营销/系统邮件常有大量重复链接，单独列出会挤占 Handle 核心操作区。
- 用户真正需要点击链接时，应该在原邮件语境中点击，并由前端确保新标签页打开。

### 6.3 CSP 与 external origins

当前 `anna-inbox/manifest.json` 的 `external_origins` 为空，且 CSP 只允许 self 脚本/样式。链接在新标签页打开不应要求 App 内加载外部 origin，因此不建议为此修改 `external_origins`。

如果 Anna Host 禁止 WebView 内 `window.open`，需要补协议确认是否存在官方 external-open API。当前工作树缺失 `.docs` 协议参考，不能凭印象写死 Host API 名称。

## 7. 前端 UI 建议

Brief 卡片新增附件 chip 区域：

```text
Attachments
[file] skill-template.s...  [PDF] YouTuber Co...  [image] image.png  +1
```

Handle 详情页逻辑：

```text
Original email body is hidden until you choose to view it.
This email has 3 attachments. Show full email to download them.
[Show full email]

展开后：
Attachments
[PDF icon] offer.pdf · 230 KB     [Download]
[XLS icon] budget.xlsx · 52 KB    [Download]
```

展示时机：

- Brief 卡片只展示附件 chip，不提供下载按钮。
- 打开卡片详情时即可知道附件元数据，但未点击 `Show full email` 前只展示提示。
- 用户点击 `Show full email` 后，附件下载列表随原文一起显示。
- `Show full email` 仍保持用户主动点击后才加载正文。

下载状态：

- 点击后按钮进入 `Preparing...`。
- 成功后触发浏览器下载。
- 失败时显示简短错误，不泄露内部路径或 credential 信息。

链接状态：

- 不提供独立 `Open` 按钮。
- 点击原邮件正文里的链接后不改变当前 Handle 页面。
- 不在工具 iframe/WebView 内加载目标网页。

## 10. 风险与待确认

- `anna-inbox/.docs/` 协议参考当前缺失。实施前如果要声明 files/upload/download capability，必须先补读或向 Anna runtime 确认准确能力名。
- Local FilesClient 当前不支持文件操作，本地开发无法完整模拟 APS 文件下载。
- 邮件 HTML 链接来自外部发件人，必须继续经过后端清洗和前端 DOMPurify 双层过滤。
- 有些附件可能是 Gmail inline image 或签名图片；第一阶段建议只展示有 filename 且有 attachmentId 的附件。
- `download_url` 应短期有效，避免长期暴露用户附件。

## 11. 推荐实施阶段

### Phase 1：链接外部打开

- 前端补 `openExternalUrl()`。
- Handle HTML 原文区域拦截链接点击，强制新标签页打开。
- 不展示结构化 Links 区域；仅拦截原文正文中的链接点击并外部打开。
- 不改附件下载。

### Phase 2：附件元数据展示

- `get_card_detail` 返回 `attachments`。
- Handle 渲染附件列表。
- Download 按钮先置灰或提示“download support pending files capability”，直到 Phase 3 确认文件能力。

### Phase 3：附件真实下载

- 新增 `prepare_attachment_download`。
- 确认并接入 APS Files / Host transient upload。
- 返回短期 `download_url`。
- 前端点击后触发下载。

已实施 Phase 1 + Phase 2，并接入 Phase 3 的按需下载工具。若当前 runtime 没有 Anna Files/APS 文件能力，下载工具不会通过 JSON-RPC 返回附件字节，而是返回不可用错误。
