# 邮件内容预处理与完整线程回复

日期：2026-07-23  
状态：P1/P2 已接入受限后台处理  
当前基线：**App `2.1.7` / Tool `2.2.7`**

## 正文派生内容

完整邮件进入本地缓存后，保留原始 `body_text` 与 MIME payload，同时生成 `content_analysis`：

- `body`：清洗后的当前正文。
- `quoted_text`：识别出的历史引用。
- `signature`：保守识别的签名段。
- `contacts`：签名中的姓名、职位、公司、邮箱、电话。
- `body_invoice_facts`：正文中的发票号、金额、付款状态。
- `attachment_analysis`：每个附件的独立解析状态、文本与附件来源事实。

正文金额与附件金额分属不同字段，回答时不得互相替代或合并成未经证实的单一金额。

## 附件处理

后台与显式线程刷新均可解析受限附件；附件字节只在解析过程中短暂读取，不写入缓存。

| 类型 | 处理方式 |
| --- | --- |
| 文本/CSV | UTF-8 解码、有限行读取 |
| DOCX/XLSX/PPTX | ZIP/XML 受限文本读取 |
| PDF | `pypdf`，最多 30 页 |
| 图片/扫描件 | 标记 `ocr_pending:platform_interface`，等待 Anna 平台 OCR 接口 |

单附件上限 8 MiB，附件数量上限 12。超过限制、格式不支持、PDF 损坏或图片 OCR 尚无平台接口均写入明确 `status`，不会伪装为无内容。

本地 OCR 不引入 Pillow、pytesseract 或 Tesseract，以控制 PyInstaller 二进制体积。图片附件在平台接口可用前不下载字节，仅保留文件名、MIME 与待处理状态。

## 完整线程起草

用户要求对当前邮件起草回复时：

1. 刷新并缓存整个 Gmail thread，包含所有消息、正文、附件 filename 与 MIME。
2. 按时间正序组合每封邮件的清洗正文与附件事实。
3. 将线程证据交给草稿模型，而不是只传当前邮件或最近四封。
4. 总证据超过 32,000 字符时标记 `partial=true`；模型不得声称已读完未包含部分。

此路径是显式用户回复操作，可触发 Gmail thread 刷新；普通 AI 搜索仍保持 cache-only。
