# 浏览器存储分层与正文预热方案

## 目标

Inbox 工作台需要减少邮件详情打开时的等待。目标是：用户切换分类并加载当前页邮件目录后，系统在后台预热当前分类、当前页内所有邮件的正文缓存；用户打开邮件详情页时，优先从缓存读取正文，避免再向 Gmail API 拉取正文，只触发必要的 LLM 总结请求。

浏览器侧存储按数据复杂度分层：

- `localStorage` 只保存临时、简单、体积小、同步读取成本可控的数据。
- IndexedDB 保存结构复杂、体积可能增长、需要异步读写的数据，包括邮件正文缓存。
- 后端 Gmail cache / APS / local JSON 仍然是权威缓存层，IndexedDB 是前端性能缓存，不替代后端缓存。
- 多邮箱场景下，每个邮箱账号的数据必须隔离；当前邮箱、账号资料、正文缓存、UI flags 都不能混在同一个无邮箱边界的全局结构里。

## Shortwave 可验证参考

以下依据来自 Shortwave 公开文档和可公开访问的 Web App 静态资源，只作为产品架构参考，不代表 Shortwave 完整内部实现已公开：

- 官方多账号文档说明 Shortwave 支持在同一设备登录多个账号、快速切换账号，并默认保持不同账号的独立 inbox 体验，不提供默认 unified inbox。参考：https://www.shortwave.com/docs/how-tos/multi-account/
- 官方安全文档说明 Shortwave 会处理邮件以提供 search、threading、labeling、AI assistant 等能力，并声明 Shortwave 数据存储在 Google Cloud，静态加密和传输加密。参考：https://www.shortwave.com/docs/guides/security/
- `https://app.shortwave.com/` 的首屏 inline script 只从 `localStorage` 读取 `shortwave-state:app-appearance` 和 `shortwave-state:primary-color-variant`，用于主题和主色这类轻量 UI preference。
- 公开 JS bundle `https://app.shortwave.com/assets/main-1cca8d0c.js` 中存在 IndexedDB wrapper，并出现设备级数据库 `shortwave-device-settings`、`users` / `permissions` object store、按 `accountId` 保存用户、以及每账号数据库名 `shortwave-db-${accountId}` 的逻辑。hard reset 逻辑会先加载 users，再按 `accountId` 删除每个账号数据库，失败时才枚举删除所有 IndexedDB database。
- 公开 vendor bundle 中出现 Firebase Messaging 的 `fcm_token_details_db` / `fcm_token_object_Store`，这是推送 token 相关 IndexedDB 存储线索，不是 Gmail OAuth token 或邮件正文缓存依据。

未找到的依据：

- 没有找到 Shortwave 官方说明其邮件正文、线程详情、LLM summary 或 Gmail OAuth token 在浏览器端的具体存储结构。
- 因此本文档不声称 Shortwave 将邮件正文存入 IndexedDB，也不按 Shortwave 推断具体邮件正文 schema。

可借鉴结论：

- 轻量 UI preference 可以继续用 `localStorage`。
- 多账号本地数据应采用“设备级元数据库 + 每账号业务数据库”的隔离模型。
- 账号切换状态不应依赖一个全局 `localStorage` mailbox key。
- 敏感凭据不应进入浏览器 localStorage；Gmail token 仍应由后端安全存储负责。

## localStorage 边界

继续放在 `localStorage` 的数据应满足以下特征：

- 简单字符串、数字或布尔值。
- 少量 UI 状态，读取失败不影响核心功能。
- 不包含邮件正文、复杂邮件对象或可持续增长的列表。

当前可保留的数据包括：

- AI sidebar 宽度：`anna-inbox:ai-sidebar-width`。
- cached inbox banner dismiss 状态。
- 少量 UI preference 或临时开关。
- AI Ask history 若继续限制为 30 条短文本，可以暂时保留。

`anna-inbox-mailbox` 不再作为长期方案保留在 `localStorage`。当前邮箱属于账号选择状态，应迁移到 IndexedDB 的设备级 meta store，或由后端 mailbox registry 返回后再恢复。迁移期可以从旧 `localStorage` key 读取一次并写入新存储，成功后删除旧 key。

## IndexedDB 边界

以下数据应迁移或新增到 IndexedDB：

- 当前邮箱和最近使用邮箱列表。
- `anna-inbox:mail-flags:${mailbox}` 中复杂结构，尤其 `saved: Record<string, InboxMessage>`。
- `anna-inbox:contact-avatars:${mailbox}` 的头像缓存、miss 列表和更新时间。
- 邮件详情页缓存：thread page、message display body、thread assist 输入所需的正文镜像。
- 目录页预热得到的邮件正文缓存。

IndexedDB key 建议包含邮箱和 Gmail 标识，避免多邮箱串数据：

- device meta：`selected_mailbox`、`last_used_mailboxes`。
- message body：`mailbox + message_id + internal_date`。
- thread page：`mailbox + thread_id + latest_message_id`。
- contact avatar：`mailbox + email`。
- UI flags：`mailbox + message_id`。

正文缓存需要保存最小可用字段：

- `mailbox`
- `message_id`
- `thread_id`
- `internal_date`
- `subject`
- `from`
- `to`
- `date`
- `body_text`
- `body_html` 或已清洗的 display HTML
- `attachments` 元数据
- `updated_at`
- `expires_at`

附件二进制不进入 IndexedDB。附件仍通过现有 Host upload、APS files 或 loopback URL 流程访问。

## 多邮箱隔离

多邮箱模式下，前端 IndexedDB 需要按邮箱账号隔离数据。借鉴 Shortwave 公开 bundle 中可见的 `shortwave-device-settings` 和 `shortwave-db-${accountId}` 结构，Anna Inbox 推荐采用“设备级数据库 + 每账号数据库”模型，而不是把所有账号混在一个大 database 里。

推荐数据库：

- `anna-inbox-device`：设备级元信息，只保存账号列表、当前邮箱、最近使用邮箱、权限状态、本地 schema 版本等。
- `anna-inbox-mailbox-${mailboxHash}`：单个邮箱账号的业务缓存，保存该邮箱的邮件正文、thread page、flags、联系人头像等。

`anna-inbox-device` 推荐 object store：

- `app_meta`：当前邮箱、最近使用邮箱、全局 UI 配置版本。
- `mailboxes`：邮箱账号展示信息和本地索引，不保存 access token 或 refresh token。
- `permissions`：浏览器通知、People API 提示等非敏感权限状态。

每个 `anna-inbox-mailbox-${mailboxHash}` 推荐 object store：

- `message_bodies`：按 `message_id/internal_date` 保存正文缓存。
- `thread_pages`：按 `thread_id/latest_message_id` 保存详情页缓存。
- `mail_flags`：按 `message_id` 保存 Todo、Done、Snooze、saved message mirror 等状态。
- `contact_avatars`：按 `email` 保存联系人头像缓存。
- `draft_mirror`：可选，保存前端草稿镜像；后端 draft storage 仍是权威来源。

清理策略也必须按邮箱执行：

- 删除某个 mailbox data 时，删除该邮箱对应的 `anna-inbox-mailbox-${mailboxHash}` database，并从 `anna-inbox-device.mailboxes` 移除账号索引。
- reset all data 时先读取 `anna-inbox-device.mailboxes`，逐个删除邮箱数据库，最后删除设备级数据库；兜底时才枚举并删除所有 Anna Inbox IndexedDB database。
- 切换邮箱只切换读取范围，不复用上一个邮箱的正文、flags 或联系人缓存。

## 凭据与个人信息

Token、授权信息和个人敏感信息不应进入浏览器 `localStorage`。也不建议把 Gmail access token、refresh token 放入浏览器 IndexedDB。

凭据类数据应由后端安全存储负责：

- Gmail access token / refresh token。
- OAuth 授权状态和 token 过期时间。
- 与账号绑定的敏感 profile 字段。

前端 IndexedDB 只保存展示所需的非敏感账号资料：

- mailbox email。
- display name。
- avatar URL。
- provider。
- selected / last used 状态。
- 最近一次授权检查状态和时间。

如果需要把 token 从当前本地 token 文件或运行时 credentials 迁入数据库，必须在后端完成，并满足项目安全约束：不新增密钥工具参数，不记录 token、authorization header 或完整 credential context，不把凭据放入 JSON-RPC result。

## 正文预热流程

触发时机：用户切换邮箱分类或加载更多时，当前分类当前页目录加载完成后触发预热。

预热范围：

- 只预热当前分类。
- 只预热当前页。
- 当前页大小沿用现有目录分页，默认 100 封。
- 不跨分类、不全邮箱扫描、不无边界预热历史邮件。

流程：

1. 前端调用目录接口加载 compact message list。
2. 目录渲染不等待正文预热完成。
3. 前端把当前页的 `mailbox/message_id/thread_id/internal_date` 传给后端预热接口，或由后端在目录接口完成后自动启动预热。
4. 后端对缺失正文的邮件并发受控拉取 Gmail full body，并写入后端 Gmail cache。
5. 后端返回或通知可缓存的正文结果时，前端写入 IndexedDB。
6. 用户打开详情页时，前端先读 IndexedDB。
7. IndexedDB 命中时立即展示详情正文，并调用 LLM 总结。
8. IndexedDB 未命中时调用后端详情接口；后端优先读本地/APS cache，原则上不再打 Gmail API。

## cache miss 策略

详情页遇到正文未命中时，默认策略应是可观测、可恢复：

- 前端显示正文加载状态。
- 后端优先读后端 cache。
- 如果后端 cache 也未命中，触发或等待预热任务。
- 不在详情页同步阻塞式拉取大量 Gmail 正文。

是否允许详情页 cache miss 时兜底调用 Gmail API，需要作为显式实现开关。当前目标是打开详情页后避免 Gmail API 正文拉取，因此默认不走兜底。

## 失效策略

正文缓存需要避免展示旧内容：

- `internal_date` 或 `latest_message_id` 变化时视为新版本。
- Gmail label 状态可以局部 patch，但正文内容不应只靠 label 变化失效。
- IndexedDB 缓存建议设置 TTL，第一版可选 7 天或 30 天。
- 用户切换账号、删除 mailbox data 或 reset all data 时，需要清理对应 mailbox 的 IndexedDB 记录。
- 当前邮箱选择状态从 `localStorage` 迁移到 IndexedDB 后，应用启动需要支持异步恢复；恢复完成前可以展示连接/加载状态。

## 性能约束

预热需要保护首屏和 Gmail API：

- 目录首屏不等待预热完成。
- 后端预热并发限制建议 5-10。
- 每次只处理当前页，避免切换分类时堆积过多后台任务。
- 新分类加载开始时，旧分类未完成预热可以取消或降级。
- IndexedDB 写入批量化，避免每封邮件触发过多 React state 更新。
- 前端不要把正文写入 React 全局 state 的大列表；详情页按需读取。

## 实现拆分建议

第一阶段：存储分层

- 新增 IndexedDB facade，统一封装 open、get、put、delete、clearMailbox。
- 新增设备级 IndexedDB：`anna-inbox-device`。
- 将当前邮箱从 `anna-inbox-mailbox` 迁移到 `anna-inbox-device.app_meta`。
- 将复杂 `mail-flags` 和 contact avatar cache 从 localStorage 迁移到 IndexedDB。
- 保留 localStorage 小配置。

第二阶段：多邮箱账号数据库隔离

- 增加 `mailboxes` store，保存非敏感账号资料和展示信息。
- 为每个邮箱创建独立业务数据库：`anna-inbox-mailbox-${mailboxHash}`。
- 增加按邮箱删除数据库能力，和后端 `deleteMailboxData` / `resetAllData` 对齐。
- 后端规划 token / 授权状态 / 敏感 profile 的安全数据库存储，不进入浏览器缓存。

第三阶段：正文缓存

- 为 message display body / thread page 增加 IndexedDB 读写。
- 详情页打开时先查 IndexedDB，再查后端 cache。
- 使用 `mailbox + message_id + internal_date` 和 `mailbox + thread_id + latest_message_id` 做缓存命中判断。

第四阶段：分类当前页预热

- 分类目录加载完成后触发当前页正文预热。
- 后端增加受控并发的正文 hydrate 能力。
- 前端接收预热结果后写 IndexedDB，或只依赖后端 cache，详情页按需拉取后写入 IndexedDB。

第五阶段：观测

- 记录目录加载耗时、预热耗时、预热命中率、详情页 IndexedDB 命中率、后端 cache 命中率、Gmail fallback 次数。
- 记录 IndexedDB 容量和每个 mailbox 的正文缓存数量。

## 非目标

- 不把全量邮箱正文一次性塞入 IndexedDB。
- 不把正文或复杂邮件对象写入 localStorage。
- 不把当前邮箱作为长期状态保存在 localStorage。
- 不把 Gmail access token 或 refresh token 放入浏览器 localStorage / IndexedDB。
- 不让目录接口一次性返回所有 full body。
- 不把 IndexedDB 作为权威数据源。
- 不改变 Gmail mutation 的用户确认边界。
