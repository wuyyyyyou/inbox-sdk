# 邮件详情抽屉改造方案

> 日期：2026-07-01；附件专项修订：2026-07-06  
> 状态：待审批；抽屉主体已部分实施，本次补充聚焦附件下载与预览修复  
> 范围：Inbox 首页点击邮件后的详情、线程原文、附件预览、AI 辅助回复和发送  
> 参考：需求示例图 1～7、2026-07-06 附件问题截图、当前 `HomeView` / `mail-detail`、现有 Brief/Handle、Gmail adapter 与附件下载链路

## 1. 目标

将当前“点击邮件后在列表行下方展开纯文本预览”改为独立的邮件详情抽屉，使用户可以在不离开 Inbox 的情况下完成以下工作：

1. 查看完整邮件线程，并默认定位到最下面的最新邮件。
2. 查看发件人、收件人、抄送等完整参与者信息。
3. 尽量按原邮件样式展示 HTML、链接、内嵌图片和附件。
4. 查看 AI 线程概述和 AI 生成的快捷回复建议。
5. 展开回复编辑器、生成 AI 草稿并真实发送 Gmail 回复。
6. 在详情顶部执行未读、重要、Todo、Snooze、Trash、Done 等操作。

本方案优先保证数据正确、安全和可分段交付，不把示例产品中暂时没有后端能力的功能伪装成可用功能。

## 2. 本次不做的内容

- 不整体重设计 Inbox 列表、左侧 Anna 对话区、邮箱目录或全局导航；左侧 Anna 仅新增“邮件上下文 prompt、draft artifact 与插入/复制动作”。
- 不引入路由库、状态管理库、UI 组件库、图标库、Tailwind 或 CSS-in-JS。
- 不实现 Forward、Reply all、标签管理、打印、屏蔽垃圾邮件等未要求功能。
- 第一版不实现富文本 HTML 邮件发送、回复附件、定时发送和后台提醒任务。
- 不把附件字节或超长原始邮件通过 JSON-RPC result 直接返回。
- 不提交 `bundle/` 构建产物。

## 3. 当前实现基线

### 3.1 前端现状

- `src/features/home/HomeView.tsx` 使用 `selectedId` 控制选中邮件。
- `InboxRow` 在选中行下方直接渲染 `mail-preview-panel`。
- `loadInboxEmailBody()` 通过 `get_cached_email` 取得单封邮件，只向页面返回字符串正文。
- 列表层已经有 Star、Todo、Snooze、Mark read、Trash、Done 图标。
- Star、Mark read 和 Trash 已调用 Gmail 工具；Todo、Snooze、Done 仍是 `localStorage` 中的 UI 标记。
- `src/features/handle/HandleView.tsx` 已有 `DOMPurify` 安全渲染 HTML、线程摘要、草稿、附件下载等可复用经验，但它的数据入口绑定 Brief card。

### 3.2 后端现状

| 能力 | 当前状态 | 详情页可用性 |
|---|---|---|
| 单邮件元数据/正文 | `get_cached_email(mailbox, message_id)` | 可复用，但不足以展示完整 thread |
| Gmail thread 拉取与缓存 | adapter 内已有 `refresh_thread_cache`、`get_thread_context` 等内部能力 | 可复用内部逻辑，需要新增 Inbox 工具入口 |
| 原始 HTML 提取 | adapter 已有用户展示用正文提取，缓存中保留 MIME payload | 可复用，但需形成稳定 DTO |
| HTML 安全渲染 | 前端 Handle 已使用 `DOMPurify` | 可抽成共享组件 |
| 线程 AI 概述 | `summarize_thread` / `start_summarize_thread` | 绑定 `card_id`，不能直接用于任意 Inbox thread |
| AI 草稿 | `generate_draft_reply` 绑定 card；`generate_ask_draft` 要求 `user_answers` | 可复用 service/prompt，不可直接复用现有调用契约 |
| AI 快捷 prompt | 左侧 Anna 已有对话能力，但没有“当前邮件上下文引用”和 draft artifact | 需要新增上下文桥接与结构化结果 |
| Mark read | `mark_read_from_ask` 只支持移除 `UNREAD` | 可用于已读；Mark unread 需要新增反向写入 |
| Star | `set_message_starred` 操作 Gmail `STARRED` | 与本需求的 Important 不是同一状态 |
| Important | 列表能读取 `IMPORTANT`，没有写工具 | 需要新增 `IMPORTANT` label 写入 |
| Trash | `trash_from_ask` | 可复用 |
| Todo/Snooze/Done | Home 当前只写 `localStorage` | 第一版可延续；推荐后续统一到 mailbox-scoped storage |
| 真实发送回复 | `reply_from_ask` / `send_reply` | 可复用；当前只发送 `text/plain` |
| 附件下载 | `prepare_attachment_download` | 绑定 `card_id`，任意 Inbox 邮件不可直接使用 |
| 附件预览 | 无独立 preview 模式 | 需要新增短期 inline URL，并验证 Anna CSP/runtime |

结论：该改造不是纯前端换壳。抽屉骨架和单邮件正文可先做，但“完整线程、AI 概述、快捷 prompt、任意 Inbox 附件、Mark unread/Important”都需要薄后端适配。

## 4. 信息架构与布局

### 4.1 抽屉形态

- 点击邮件后，在邮件工作区上方打开右侧详情抽屉，不再在列表行内展开。
- 打开抽屉后，触发它的邮件行保持选中状态，使用浅蓝背景和左侧蓝色强调线；只有关闭详情或切换到另一封邮件时才清除/迁移选中态。
- 左侧 Anna 区保持可见；邮件列表作为抽屉后的背景上下文保留。
- 桌面端建议宽度 `min(960px, calc(100vw - AI sidebar - account rail - 24px))`，最小宽度约 `620px`。
- 窄窗口（建议 `< 900px`）使用全屏详情层，避免正文和回复区过窄。
- Drawer 根节点不设置纵向滚动条，使用 `display: flex; flex-direction: column; height: 100%; overflow: hidden`。
- Header 和 Footer 都使用正常布局中的 `position: relative`，不使用 `sticky` 或 `fixed`；只有中间的邮件上下文区域使用 `overflow-y: auto`。
- 只能点击顶部 Close thread 按钮关闭详情。`Esc`、点击遮罩、再次点击已选中邮件行都不得关闭 Drawer；`Esc` 只允许关闭当前打开的 popover、Snooze 弹窗或附件预览层。
- 关闭后焦点返回触发该抽屉的邮件行。

### 4.2 页面从上到下

```text
┌ Header（position: relative，不滚动）────────────────────┐
│ Close | Mark unread | Important | Todo | Snooze | Trash | Done │
│ Subject / AI overview / Participants                    │
└─────────────────────────────────────────────────────────┘
  ┌ Thread context（唯一主滚动区，oldest -> newest）──────┐
  │ message 1 header + original content + attachments     │
  │ message 2 header + original content + attachments     │
  │ ...                                                   │
  │ latest message                                        │
  └───────────────────────────────────────────────────────┘
┌ Footer（position: relative，不滚动）────────────────────┐
│ AI quick replies                                        │
│ Collapsed reply row / Expanded reply editor             │
└─────────────────────────────────────────────────────────┘
```

标题、AI 概述和参与者区属于线程头部；每封邮件有自己的发送者、时间、正文和附件，不能把整条线程的附件都错误归到最新邮件下。

## 5. 详细交互

### 5.1 打开、关闭与默认滚动

打开流程：

1. 点击列表邮件后立即打开抽屉 shell，并显示该行已有的 subject/from/snippet，避免等待空白页。
   同时将该邮件行置为持续选中态；选中态由 `mailbox + message_id` 驱动，不依赖 hover 或键盘焦点。
2. 请求线程元数据和最新一页消息。
3. 最新一页完成布局后，使用 `useLayoutEffect + requestAnimationFrame` 将“邮件上下文滚动容器”定位到末尾。
4. AI 概述和快捷回复并行加载，不阻塞原文展示。
5. 更早的线程页从顶部向前补齐；prepend 前后记录 `scrollHeight` 差值，保持用户当前视觉位置。

滚动规则：

- “滚动到底部”只指中间的邮件上下文容器；Drawer、Header、Footer 均不能出现页面级纵向滚动条。
- 首次打开时，邮件上下文容器默认滚到最新消息。
- 用户主动滚动上下文后，后续异步结果不得把上下文再次强制拉到底部。
- 在抽屉内切换到另一封邮件时，重新执行首次定位。
- 线程加载失败时保留当前单邮件作为降级内容，并显示 Retry。
- Footer 中的回复编辑器展开后，通过 flex 布局压缩上下文区域高度；展开/折叠不能改变 Header 位置。超长草稿只允许编辑器文本区域自身滚动。

### 5.2 顶部功能菜单

| 操作 | 第一版语义 | 实现 |
|---|---|---|
| Close thread | 关闭详情抽屉，不修改邮件状态 | 前端本地状态 |
| Mark as unread | 给当前最新 inbound message 增加 Gmail `UNREAD` | 新增通用 label modify 工具 |
| Mark important / not important | 切换 Gmail `IMPORTANT`，不是 `STARRED` | 新增 `set_message_important` |
| Add to todo | 加入 Anna Inbox Todo | 先复用 Home 标记；后续迁移 APS/local storage |
| Snooze | 先打开统一的 `Snooze until` 弹窗，用户选择时间后才隐藏邮件并记录恢复时间 | 新增共享 Snooze picker；持久状态建议走 storage_ops |
| Trash | 将线程中的目标邮件移入 Gmail Trash；成功后关闭抽屉 | 复用/泛化 Trash 工具 |
| Done | 标记为 Anna Inbox 已完成并从 Inbox 过滤 | 应用状态，不伪装成 Gmail 原生状态 |

所有 Gmail 写操作采用“按钮 loading → 后端成功 → patch 列表和详情状态”的流程。Important 可以乐观更新，但失败必须回滚。Trash 不做乐观删除，避免 Gmail 写失败后邮件消失。

按钮必须有 `aria-label`、tooltip、键盘焦点样式和禁用态。Tooltip 文案根据状态变化，例如 `Mark important` / `Mark not important`。

Snooze picker 必须作为共享组件供邮件行、详情 Drawer 以及其他 Snooze 入口复用，所有 Snooze 都先选择时间，不能点击图标后立即执行。弹窗结构参考示例图 2：

- 顶部标题 `SNOOZE UNTIL`。
- 可输入自然时间，例如 `4 hours`；解析失败时提示格式错误，不关闭弹窗。
- 快捷项至少包含 `Tomorrow`、`This weekend`、`Next week`、一个动态推荐日期和 `Pick a time`。
- 每个快捷项右侧显示解析后的绝对日期、星期和时间。
- `Pick a time` 打开日期时间选择器。
- 时间按用户本地时区展示，持久化为带时区的 ISO 时间；到期判断使用绝对时间。
- 只有选择有效时间后才执行 Snooze。点击外部或 Cancel 只关闭弹窗，不修改邮件状态。

### 5.3 标题与 AI 概述

- Subject 使用线程最新可用标题；空标题显示 `(no subject)`。
- 概述显示为一到两句，不直接重复 subject。
- 首次打开后异步生成；同一 `mailbox + thread_id + latest_message_id` 的结果应缓存。
- 新消息进入线程后，cache key 变化并重新生成，防止使用旧概述。
- AI 不可用或生成失败时，不使用 snippet 冒充 AI 概述。概述区域明确显示 `AI is unavailable`（或对应错误提示）和 `Retry` 按钮；原文仍可正常查看。
- 复用 `actions/service.py` 的 thread summary prompt 与 JSON repair，但新增基于 thread/message 的入口，不构造临时 PersistentCard 写入 active cards。

### 5.4 参与者下拉框

默认显示去重后的参与者摘要，例如 `Eric & You`。展开后按消息头展示：

```text
From:  Eric Tech — techwitheric@gmail.com
To:    kateqh@anna.partners
Cc:    ...（有值才显示）
Bcc:   ...（仅当前账户可见且有值时显示）
```

- 展示名和邮箱分别解析，邮箱保留原值供复制。
- 多发件人线程按参与者去重，不只读取最新邮件。
- `You` 根据当前 mailbox 判断，不能硬编码。
- 下拉按钮使用 `aria-expanded` / `aria-controls`。

### 5.5 线程原文

- 消息按 `internal_date` 从旧到新排序。
- 每封消息头展示头像/首字母、发送者、日期时间和收件信息。
- 默认展开最新消息；更早消息可以紧凑展示标题行，但为了满足“全部上下文”，后台加载完成后均可展开查看全文。
- HTML 邮件优先展示安全清洗后的 HTML；无 HTML 时展示纯文本并保留换行。
- 链接强制 `target="_blank" rel="noopener noreferrer"`。
- 使用共享 `SafeEmailHtml` 组件封装 DOMPurify allowlist，不在多个页面复制 `dangerouslySetInnerHTML` 配置。
- 禁止 script、iframe、object、embed、form、事件属性、`javascript:`/`vbscript:` URL。
- 远程图片默认允许 lazy load，但不得携带 Anna/Gmail 凭据；加载失败显示占位。
- CID 内嵌图片复用后端已有解析能力。超大图片不应被内联进 JSON-RPC。

为了控制 stdio payload，线程接口按页返回消息元数据和有上限的显示正文。超长正文应按消息按需加载，不能一次返回无限长度线程。

### 5.6 附件列表、预览与下载

每封消息正文下方展示附件 chip/card：文件名、类型、大小、Preview、Download。

第一版预览矩阵：

| 类型 | 预览方式 | 降级 |
|---|---|---|
| PNG/JPEG/GIF/WebP | 详情页内图片预览 modal | Download |
| PDF | 浏览器原生 `iframe/object` 预览 modal | 新窗口打开或 Download |
| text/plain、JSON、CSV | 安全 text viewer，限制预览大小 | Download |
| MP4/WebM、MP3/WAV | 浏览器原生 media controls（runtime 支持时） | Download |
| DOCX/XLSX/PPTX、压缩包及未知格式 | 第一版不做内容解析 | Download only |

预览 modal 参考示例图 5：

- 顶部显示 `当前序号 / 可预览总数 - filename`。
- 支持上一项、下一项、关闭、下载当前项、Download all。
- `Download all` 第一版逐个请求短期 URL，不在前端拼接 zip；若浏览器拦截批量下载则提示用户逐个下载。
- 关闭预览后回到原附件按钮，并保持详情滚动位置。

后端需要把现有 card-bound 附件访问泛化为 Inbox message/thread 访问，并支持 `mode=preview|download`：

- `preview` 返回短期 inline URL。
- `download` 返回短期 attachment URL。
- 两种模式都只返回 URL、文件元数据和过期时间，不返回附件字节。
- opaque attachment id 必须在对应 mailbox/message MIME 元数据中重新校验，不能信任前端传入的 Gmail attachmentId。

PDF inline preview 受 Anna Runtime CSP、预签名 URL 的 `Content-Disposition` 和跨域策略影响。实施附件阶段前必须做一个 runtime spike：Host URL、APS URL、local loopback URL 各验证一次。无法满足 inline preview 时保留明确的“Open preview externally / Download”降级，不扩大到不受控的任意外部 origin。

#### 5.6.1 2026-07-06 附件问题复盘与修复原则

当前抽屉已接入 `prepare_inbox_attachment_access`，但从截图可见 PDF 附件只展示 `Download`，没有 `Preview`；点击下载/预览也存在不可用情况。结合现有实现，问题集中在以下几类：

1. 前端只根据 `mime_type` 判断能否预览；当 Gmail/缓存返回空 MIME、`application/octet-stream` 或非标准 MIME 时，`.pdf` 文件不会显示 `Preview`。
2. 邮件详情抽屉只读取 `preview_url` / `download_url`，没有像 Handle 附件下载那样兼容 `delivery="inline"` + `content_b64` 的返回；当后端为小附件走 inline fallback 时，前端会认为“没有 URL”。
3. 下载路径目前使用 `window.open(url)`，没有稳定的 `<a download>` 触发、文件名兜底、Blob URL 生成与释放、失败 toast，也无法清楚区分“浏览器拦截”“工具返回错误”“URL 过期”。
4. 预览路径没有独立的 loading/error 状态；短链准备失败、PDF 被 CSP/frame 策略拦截、文本 fetch 失败时，用户只看到无响应或空白。
5. `Download all` 直接复用单个 `openAttachment`，会同时修改预览状态并批量打开窗口，容易被浏览器拦截，也不利于逐项错误提示。

修复原则：

- 附件字节仍不得通过 JSON-RPC result 传大文件；inline fallback 只允许沿用现有小附件上限。
- 任意下载/预览前都必须重新用 `mailbox + message_id + opaque attachment_id` 在后端校验归属，不能信任前端传入的 Gmail `attachmentId`。
- PDF、图片、文本等可预览类型要同时参考 `mime_type` 和安全的文件扩展名；扩展名只用于 UI 能力判断，不用于绕过后端归属校验。
- 前端必须兼容三种合法结果：URL、inline base64、明确错误；三者外的返回一律显示可理解的错误，而不是静默失败。
- 预览失败时必须保留 `Download` 降级；下载失败时不关闭抽屉、不改变邮件状态。

#### 5.6.2 附件 access 返回契约修订

`prepare_inbox_attachment_access` 保持现有工具名，返回结构补充以下约定，避免重新设计协议：

```ts
interface AttachmentAccessPayload {
  ok: boolean;
  delivery: "url" | "inline";
  mode: "preview" | "download";
  filename: string;
  mime_type: string;
  size: number;
  download_url?: string;
  preview_url?: string;
  content_b64?: string;
  expires_at?: string;
  error?: string;
  message_id: string;
  attachment_id: string;
}
```

约定：

- `ok === false` 时前端必须展示 `error`，不再尝试打开 URL。
- `delivery="url"` 时：
  - `download` 模式使用 `download_url`。
  - `preview` 模式优先使用 `preview_url`，缺失时可用 `download_url` 做外部打开降级，但 UI 要标明不是 inline preview。
- `delivery="inline"` 时：
  - 前端用 `content_b64 + mime_type` 构造 Blob URL。
  - `download` 使用 Blob URL + `<a download>`。
  - `preview` 使用 Blob URL 填充 `img`、`iframe`、`audio/video` 或文本 viewer。
- `expires_at` 过期或 URL 打开失败时，前端重新请求一次 access；重试仍失败才提示用户。
- 后端返回的 `mime_type` 应尽量规范化；为空时至少返回 `application/octet-stream`。前端展示时可隐藏这个兜底 MIME，避免 UI 噪音。

#### 5.6.3 前端修复设计

新增或调整共享 helper，供详情抽屉和后续 Handle 复用：

```ts
type AttachmentKind = "pdf" | "image" | "text" | "audio" | "video" | "download";

normalizeAttachmentKind(attachment): AttachmentKind
resolveAttachmentAccess(payload): { kind: "url" | "blob"; url: string; revoke?: () => void }
triggerAttachmentDownload(access, filename): void
```

类型识别规则：

- `application/pdf` 或文件名 `.pdf` -> `pdf`。
- `image/*` 或 `.png/.jpg/.jpeg/.gif/.webp` -> `image`。
- `text/*`、`application/json`、`text/csv` 或 `.txt/.json/.csv/.log/.md` -> `text`。
- `audio/*`、`video/*` 仍按 MIME 优先；扩展名只覆盖常见 `.mp3/.wav/.mp4/.webm`。
- DOCX/XLSX/PPTX、zip、未知类型 -> `download`。

交互修复：

- 附件 card 对 `pdf/image/text/audio/video` 显示 `Preview` 和 `Download`；不可预览类型只显示 `Download`。
- 点击 `Preview` 后立即打开 modal 并显示 loading，再请求 `prepare_inbox_attachment_access(mode="preview")`；失败时 modal 内显示错误、`Retry` 和 `Download`。
- PDF 预览优先使用 `<iframe src={blobOrPreviewUrl}>`；若 Anna Runtime 阻止 iframe/blob/loopback，则显示 `Open preview externally` 与 `Download`。
- 文本预览限制最大读取和渲染大小，超限显示截断提示和 `Download`。
- 点击 `Download` 使用统一下载函数：URL 走 `<a download>`，inline 走 Blob URL；不再直接裸 `window.open`。
- `Download all` 改为顺序下载可下载附件，逐项准备 access；每项间隔一个短 tick，失败项汇总 toast，不再复用会打开预览 modal 的函数。
- 预览 modal 关闭时释放当前 Blob URL，切换附件时释放上一项 Blob URL，避免内存泄漏。

#### 5.6.4 后端修复设计

后端以最小变更稳定现有接口：

- `attachment_metadata_from_message` 保留 opaque id，但补充 MIME 规范化：空值统一为 `application/octet-stream`，并在必要时可根据安全扩展名补充 `display_mime_type` 或由前端兜底判断。
- `prepare_inbox_attachment_access(mode="preview")` 不应只固定走 loopback；应按 runtime 能力选择：
  1. 可生成 host/APS inline-capable URL 时返回 `preview_url`。
  2. 本地开发或 host 不可用时返回 loopback inline URL。
  3. 小附件且 URL 通道不可用时返回 `delivery="inline" + content_b64`。
  4. 以上都不可用时返回 `ok=false` 和可读错误。
- `prepare_inbox_attachment_access(mode="download")` 可继续优先 host/APS URL，但必须保留 inline 小附件 fallback，并在返回中明确 `delivery`。
- 对 PDF 预览需要确认响应 `Content-Type: application/pdf`，inline URL 的 `Content-Disposition` 尽量为 `inline`；下载 URL 为 `attachment`。
- 任何 host upload / APS upload / loopback 失败都写 `stderr` 日志，不写 `stdout`，返回给前端的是短错误摘要。

#### 5.6.5 CSP 与 runtime spike

附件预览涉及 URL、Blob 和 iframe/media，实施前必须验证当前 Anna Runtime 的实际策略。当前 `anna-inbox/manifest.json` 已允许 `img-src blob: https:`，但 PDF iframe、文本 fetch、audio/video 可能还需要补充：

- `frame-src` / `child-src`: `blob:`，必要时仅本地开发允许 `http://127.0.0.1:*`。
- `media-src`: `blob:`，必要时仅本地开发允许 `http://127.0.0.1:*`。
- `connect-src`: host/APS 短链域名，必要时仅本地开发允许 `http://127.0.0.1:*`。

若平台不允许这些来源，第一版保持安全降级：图片可用 `<img>` 预览则内嵌；PDF 显示 `Open preview externally` / `Download`，不为了预览放宽到任意外部 origin。

### 5.7 AI 快捷 prompt

- 在线程正文后、回复区前展示最多 3 个短建议，例如 `Sounds good!`、`Thanks for the update`。
- 每项是 AI 根据完整线程生成的“回复意图”，不是直接发送按钮。
- 点击快捷 prompt 后，不直接调用隐藏的 draft API，也不直接修改回复编辑器；它会向左侧 Anna AI 工具发送一条可见 prompt，例如 `Reply to this email and expand on "Sounds good!"`。
- 发送 prompt 时附带不可见的当前邮件上下文引用：`mailbox + thread_id + anchor_message_id + latest_message_id`。Anna 根据该引用读取完整线程，不能只依赖 prompt 文本或当前 DOM。
- 左侧 AI 对话区立即显示用户 prompt、读取线程的进度和 AI 回复。AI 生成结果必须包含结构化 `draft_reply` artifact，而不只是普通聊天文本。
- draft artifact 提供以下操作：
  - `Insert draft reply`：展开当前 Drawer 的回复编辑器，并将 draft 插入当前 thread 的草稿。
  - 更多菜单 `Insert into new email`：将 draft 带入新邮件编辑入口；如果 Compose 尚未实现，该项明确禁用并显示 `Coming later`。
  - 更多菜单 `Copy draft`：复制纯文本 draft，并显示成功/失败反馈。
- `Insert draft reply` 覆盖已有非空草稿前必须确认；插入后焦点进入编辑区，仍需用户点击 Send。
- 不允许点击 chip 直接发送邮件。
- AI 不可用或生成失败时，左侧 AI 对话展示错误和 Retry；快捷 prompt 保持可见以便重试，不生成虚假 draft。
- 建议和概述可由同一次结构化 LLM 调用生成，以减少延迟和成本：

```json
{
  "overview": "Anna and Eric are finalizing the recording scope.",
  "quick_replies": [
    {"id": "confirm", "label": "Confirm the plan", "intent": "Confirm and thank Eric."},
    {"id": "ask_timing", "label": "Ask for timing", "intent": "Ask for the exact Thursday timing."}
  ]
}
```

### 5.8 回复区

默认折叠，只显示收件人和右侧 Reply 箭头。点击后：

- 展开纯文本编辑区并聚焦。
- 从最新 inbound 消息计算 `To`，不能回复给当前 mailbox 自己。
- 自动读取该 thread 已保存的本地/APS 草稿。
- 编辑区右上角提供 Expand inline 和 Discard draft。
- Expand inline 只改变编辑区域高度/覆盖布局，不新开窗口。
- Discard draft 在非空草稿时需要确认，并清除持久草稿。
- 当编辑区内容为空、AI draft 未在生成、没有打开编辑器内菜单，且用户点击回复区以外的内容时，编辑区自动折叠。
- 自动折叠使用短动画，例如 `max-height + opacity + transform`，时长建议 `160～220ms`；动画结束后 Footer 回到折叠高度，上下文区域自然扩展。
- 编辑区只要存在文字、未保存变更或 AI 正在生成，就不得因外部点击自动折叠。`Esc` 也不负责折叠编辑器。

第一版编辑工具区只实现与 `text/plain` 发送一致的能力：

- Bulleted list：给选中行增加/移除 `- `。
- Numbered list：给选中行增加编号。
- Insert link：插入可见 URL 文本。
- AI draft：向左侧 Anna AI 工具发送 prompt，AI 返回可插入的 draft artifact；不直接发送邮件。

第一版不展示会让用户误以为可发送富文本的 Bold、Font、Image 等无效按钮。后续若升级 `send_reply` 为 `multipart/alternative`，再增加真正的富文本工具栏。

### 5.9 AI draft 与发送

AI draft：

- 点击 AI draft 后，向左侧 Anna AI 工具发送固定可见 prompt：`Write a first draft reply to the current thread`。
- 同快捷 prompt 一样，请求附带当前邮件上下文引用 `mailbox + thread_id + anchor_message_id + latest_message_id`，让 Anna 将该 prompt 与当前 Drawer 的完整线程关联。
- 左侧 AI 对话显示该 prompt 和生成过程；AI 复用现有 draft service 的事实约束、reply gap 和 JSON repair。
- AI 返回结构化 `draft_reply` artifact，并提供 `Insert draft reply`、`Insert into new email`、`Copy draft`。只有用户点击 `Insert draft reply` 后，内容才写入当前编辑器。
- 如果缺少只有用户知道的信息，AI 对话先询问 reply gap；拿到回答后再生成 artifact。
- AI 生成前保留用户已有文本；插入结果覆盖已有非空草稿时先确认。

发送：

- 主按钮 `Send` 使用现有 Gmail `send_reply` 路径，默认 `dry_run=false` 仅在用户明确点击后执行。
- 发送中禁用重复点击；使用客户端 request id 或后端幂等保护，避免超时重试导致重复发送。
- 成功后刷新 thread cache、清除草稿、在正文底部追加 sent message，并保持滚动到底部。
- 失败时保留草稿并显示可重试错误，不关闭详情。

第一版发送下拉菜单建议：

1. `Send`：立即发送。
2. `Send & done`：发送成功后再标记 Done；若 Done 写入失败，邮件仍算已发送并提示部分成功。
3. `Send & remind`：暂不启用，直到有可靠的持久 reminder/唤醒机制。
4. `Schedule send`：暂不启用；Gmail API 没有可直接复用的原生 schedule-send 调用，不能依赖 Executa 进程长期驻留。

为了满足“按钮和下拉框要做”，第一版可显示完整菜单结构，但未实现项必须有 `Coming later` 和禁用态，不能点击后静默失败。若审批要求第一版全部可用，需要单独增加持久调度服务设计，不应塞入本次 UI 改造。

## 7. 推荐 DTO 与工具契约

工具名在实施时必须同步 `main.py` 内嵌 manifest、`inbox-tool/manifest.json` 和 app stub。以下为审批用草案。

### 7.1 线程详情分页

```text
get_inbox_thread_page(
  mailbox,
  thread_id,
  anchor_message_id?,
  before_index?,
  limit=20,
  include_display_body=true
)
```

```ts
interface InboxThreadMessage {
  id: string;
  thread_id: string;
  internal_date: string;
  from: string;
  to: string;
  cc?: string;
  bcc?: string;
  subject: string;
  label_ids: string[];
  body_text?: string;
  body_html?: string;
  body_truncated?: boolean;
  attachments: MailAttachmentMeta[];
}

interface InboxThreadPage {
  mailbox: string;
  thread_id: string;
  subject: string;
  messages: InboxThreadMessage[];
  returned_count: number;
  has_earlier: boolean;
  next_before_index: number | null;
  latest_message_id: string;
}
```

正文必须有单封上限；超限时通过 `get_inbox_message_display_body(mailbox, message_id)` 按需补取。HTML 是展示版本，LLM 仍使用清洗后的 text，不把原始 HTML 传给模型。

### 7.2 AI 线程辅助

```text
start_inbox_thread_assist(mailbox, thread_id, latest_message_id, ai_provider)
```

返回 background `run_id`，结果包含 `overview`、`quick_replies` 和可选 `reply_gaps`。结果以 `mailbox/thread/latest_message_id` 为小 JSON 缓存；不写入 Brief active cards。

### 7.3 左侧 Anna 邮件上下文桥接与 AI 草稿

前端统一通过一个上下文感知入口向左侧 Anna 发消息，快捷 prompt 和 AI draft 共用同一条链路：

```ts
interface AiMailContextRef {
  kind: "gmail_thread";
  mailbox: string;
  thread_id: string;
  anchor_message_id: string;
  latest_message_id: string;
}

interface SubmitMailPromptRequest {
  visiblePrompt: string;
  context: AiMailContextRef;
  expectedArtifact: "draft_reply";
}

interface DraftReplyArtifact {
  type: "draft_reply";
  mailbox: string;
  thread_id: string;
  body: string;
  source_prompt: string;
}
```

`visiblePrompt` 进入左侧聊天记录；`context` 只作为结构化上下文传递，不能把整条邮件正文拼到可见 prompt，也不能由模型根据当前页面 DOM 猜测邮件。

Anna/Executa 收到请求后，根据 context ref 读取和校验当前 mailbox/thread，再调用内部 draft service。内部仍可新增/使用 `start_inbox_generate_draft` background 工具，但前端交互入口必须是左侧 Anna 对话，而不是 Drawer 直接静默调用工具。长 LLM 调用继续使用 background run/poll 模式。

artifact action 需要校验：执行 `Insert draft reply` 时，当前打开 Drawer 的 `mailbox + thread_id` 必须仍与 artifact 一致；如果用户已切换邮件，提示重新打开对应 thread，不得把草稿插错邮件。

### 7.4 Gmail label 写入

建议新增统一工具，而不是为每个 label 重复接口：

```text
modify_message_labels(mailbox, message_ids, add_label_ids, remove_label_ids)
```

后端 allowlist 仅允许本页面需要的 `UNREAD` 和 `IMPORTANT`，防止前端任意修改系统标签。Star 现有工具可暂时保留。

### 7.5 附件访问

```text
prepare_inbox_attachment_access(
  mailbox,
  message_id,
  attachment_id,
  mode="preview" | "download"
)
```

返回现有 `AttachmentDownloadPayload` 的兼容扩展。`attachment_id` 是后端生成的 opaque id，不是长期暴露的 Gmail attachmentId。

### 7.6 草稿和应用状态

小 JSON key 建议：

```text
mailbox/<sanitized-mailbox>/inbox-thread-assist/<thread-id>/<latest-message-id>
mailbox/<sanitized-mailbox>/inbox-drafts/<thread-id>
mailbox/<sanitized-mailbox>/inbox-ui-state/<message-id>
```

所有读写继续走 `storage_ops.py`；读取用 `result.get("exists")`；并发草稿更新使用 `etag/if_match`。不要把 HTML 正文或附件放入 KV。

## 8. 分阶段实施

### Phase 0：契约与 runtime spike

目标：先消除最可能返工的附件和 thread 数据风险。

- 用真实测试邮箱验证完整 thread、HTML、CID 图片和附件元数据。
- 分别验证图片、PDF 在 Anna Runtime 中通过 Host/APS/local URL 预览。
- 确认 short URL 的 CSP、CORS、Content-Disposition 行为。
- 固化 DTO、正文上限和 preview fallback。

验收：形成可运行的最小 tool smoke，不改主 UI；确认 PDF 能否内嵌，不能则批准外部预览降级。

### Phase 1：前端抽屉骨架与单邮件降级

- 新增 `mail-detail` feature、无根滚动条的 drawer shell、relative Header/Footer、上下文独立滚动区、标题、参与者区和 Reply 折叠区。
- 移除 `InboxRow` 的 `mail-preview-panel`。
- 打开时先使用现有 `get_cached_email` 展示单邮件。
- 完成“仅 Close thread 可关闭”、焦点恢复、邮件行持续选中、窄屏全屏模式和上下文默认滚到底部。
- 接入已有 Mark read、Trash、Todo、Done；新增并统一所有入口使用的 Snooze picker。

验收：点击任意邮件不再撑开列表；触发邮件行保持蓝色选中态；Esc/遮罩/再次点击邮件行不能关闭；Drawer 根节点无滚动条；Header/Footer 不滚动；上下文默认显示最新消息；无后端新接口时仍可降级使用。

### Phase 2：完整 thread 与原文渲染

- 新增 thread page 工具和 DTO。
- 接入旧到新排序、向前分页、滚动位置保持。
- 抽取 `SafeEmailHtml`，展示 HTML、链接、CID 图片和纯文本 fallback。
- 新增 Mark unread、Important/not important。

验收：多消息线程上下文完整；默认定位最新邮件；异步加载旧消息不跳屏；HTML XSS 用例被拦截。

### Phase 3A：附件下载与预览专项修复（本次优先）

目标：修复当前已落地抽屉中“PDF 不显示 Preview、Download/Preview 无响应或空白”的问题，不扩大到 AI/回复等其他功能。

- 前端新增附件类型规范化 helper，按 MIME + 文件扩展名判断 `pdf/image/text/audio/video/download`。
- 邮件详情抽屉的附件 access 统一兼容 `download_url`、`preview_url`、`content_b64` 和 `ok=false`。
- 下载改为复用稳定 `<a download>` / Blob URL 触发逻辑，避免裸 `window.open`。
- 预览 modal 增加 loading、error、Retry、Open externally、Download 降级。
- `Download all` 改为顺序下载，不复用会修改 preview 状态的单附件函数。
- 后端补齐 `prepare_inbox_attachment_access` 的 inline fallback 与 URL/inline delivery 标识，确保小附件也可被前端消费。
- 做 PDF runtime spike：Blob URL、loopback URL、host/APS URL 至少验证一种能在当前 Anna App 中工作；不能 inline 时采用外部预览/下载降级。

验收：

- 截图中的 `.pdf` 附件即使 MIME 为空或为 `application/octet-stream`，也显示 `Preview`。
- 点击 `Download` 能保存或打开真实附件，文件名正确；URL 和 inline base64 两种返回都可用。
- 点击 `Preview` 后先出现 loading；PDF 可 inline 预览时显示在 modal 中，不可 inline 时显示明确降级按钮。
- 预览失败、URL 过期、工具返回 `ok=false` 时均有 toast 或 modal 错误，不静默失败。
- 关闭或切换预览不会泄露 Blob URL。

### Phase 3B：附件预览与下载完整体验

- 泛化附件 access 工具。
- 实现附件 card、preview modal、前后切换、下载当前项和 Download all。
- 按预览矩阵处理类型与降级。

验收：图片/PDF 在批准的 runtime 路径中可预览；未知文件只下载；大附件不进入 JSON-RPC；过期 URL 可重新获取。

### Phase 4：AI 概述与快捷 prompt

- 新增 `start_inbox_thread_assist`。
- 复用现有 summary/LLM JSON repair，输出概述和最多 3 个回复建议。
- 接入 cache、loading、`AI is unavailable + Retry`，不以 snippet 冒充 AI 概述。
- 新增 `AiMailContextRef`、左侧 Anna 邮件 prompt 桥接和 `draft_reply` artifact 展示。
- 实现 artifact 的 `Insert draft reply`、`Copy draft`，以及 Compose 未就绪时禁用的 `Insert into new email`。

验收：打开详情不等待 AI；AI 不可用时有明确提示和 Retry；点击建议后左侧出现可见 prompt，Anna 读取正确 thread 并返回 draft artifact；只有点击 `Insert draft reply` 才写入编辑器；线程新增消息后不会显示旧缓存。

### Phase 5：回复编辑器、AI draft 与发送

- 实现展开/收起动画、空编辑器外部点击自动折叠、纯文本工具、Expand inline、Discard draft。
- AI draft 向左侧 Anna 发送固定 prompt `Write a first draft reply to the current thread`，并复用 Phase 4 的 context ref/artifact 链路。
- 新增任意 Inbox thread 内部 draft service 入口和 reply gap。
- 接入真实 Send、Send & done、重复发送保护、成功后刷新 thread。
- 草稿持久化到 mailbox-scoped storage。

验收：空编辑器点击外部会平滑折叠，非空或生成中不折叠；左侧 Anna 收到固定 prompt 和正确 thread 上下文；artifact 不会插入已切换的 thread；刷新/关闭再打开后草稿可恢复；AI 不能自动发送；发送成功后 Gmail thread 可见；失败时草稿不丢失。

## 11. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 完整 thread 造成 stdio result 过大 | 分页、单邮件正文上限、按需加载，不返回附件 bytes |
| 邮件 HTML XSS/追踪 | DOMPurify、严格 allowlist、禁止危险 URL/标签、远程图片无凭据 |
| PDF/图片受 Runtime CSP 阻止 | Phase 0 spike；短期 inline URL；保留外部预览/下载降级 |
| MIME 缺失导致 PDF 不显示 Preview | 前端按安全扩展名兜底识别；后端 MIME 规范化；测试覆盖 `.pdf + application/octet-stream` |
| 小附件走 inline fallback 但前端只认 URL | 前端统一解析 `delivery=url/inline`；Blob URL 下载和预览；测试覆盖 `content_b64` |
| 批量下载被浏览器拦截 | `Download all` 顺序触发并汇总失败；保留逐个下载入口 |
| Blob URL 泄漏或预览错用旧附件 | 切换/关闭时 revoke；preview 状态按 attachment/message 双 key 管理 |
| AI 延迟拖慢打开 | 原文和 AI 并行，AI 不阻塞；按 latest_message_id 缓存 |
| 左侧 AI 将草稿插错 thread | artifact 携带 mailbox/thread id；插入时再次与当前 Drawer 校验 |
| 发送重复 | UI 锁、request id/幂等检查、超时后查询 thread 再决定是否重试 |
| 草稿丢失 | debounce 持久化；关闭前 flush；发送失败不清理 |
| Todo/Snooze/Done 多设备不一致 | 明确其为 Anna 状态；逐步从 localStorage 迁移 storage_ops |
| Snooze 相对时间受时区/夏令时影响 | 选择时解析为绝对时间并展示确认值；存储带时区 ISO 时间 |
| Mark important 与 Star 混淆 | 操作 Gmail `IMPORTANT`；图标、tooltip 和字段独立 |
| 新邮件到达后摘要陈旧 | cache key 包含 latest_message_id |
| 用户打开详情后被异步加载拉走 | `userHasScrolled` 锁；prepend 保持 scrollHeight 差值 |

## 12. 审批建议

建议整体仍按 Phase 0 → 1 → 2 → 3 → 4 → 5 执行，每阶段都可独立验收和回退。鉴于抽屉主体已部分落地且当前阻塞点是附件，本次建议先审批 Phase 3A 附件专项修复，再回到后续完整体验。

本次附件专项审批请确认以下六项：

1. 同意 PDF/图片/文本等可预览性同时参考 MIME 和安全文件扩展名；例如 `.pdf` 即使 MIME 缺失也显示 `Preview`。
2. 同意前端兼容后端 `delivery="url"` 与 `delivery="inline"` 两种附件返回；小附件 inline base64 fallback 由前端转 Blob URL 下载/预览。
3. 同意下载按钮改为稳定 `<a download>` / Blob URL 触发，不再裸 `window.open`；外部打开只作为预览降级动作。
4. 同意 PDF inline 预览受 Anna Runtime 限制时降级为 `Open preview externally` / `Download`，不为了预览放宽到任意外部 origin。
5. 同意 `Download all` 第一版顺序触发多个下载并汇总失败，不在前端打 zip。
6. 同意如 runtime spike 证明需要，最小化更新 `anna-inbox/manifest.json` 的 `csp_overrides`，仅增加附件预览必要的 `blob:`、host/APS 短链或本地开发 `127.0.0.1` 来源。

原整体改造审批仍需确认以下四项：

1. 第一版发送下拉只启用 `Send` 和 `Send & done`；`Send & remind`、`Schedule send` 显示禁用态。
2. PDF 若受 Anna Runtime CSP/预签名响应限制，允许降级为外部预览或下载。
3. Todo/Snooze/Done 第一阶段可沿用当前状态模型，但在回复阶段前迁移到 `storage_ops.py`，避免草稿和完成状态长期只存在单机 `localStorage`。
4. AI draft artifact 的 `Insert into new email` 在 Compose 未接入时显示禁用态；`Insert draft reply` 和 `Copy draft` 第一版完整可用。

如果本次仅审批附件专项，我将只实施 Phase 3A，不改 AI、发送、Snooze 或其他抽屉功能。
